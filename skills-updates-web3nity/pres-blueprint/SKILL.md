# Pres-Blueprint — смысловая фаза презентации

Помоги пользователю принять смысловые решения ДО того, как начнётся производство слайдов.
Принимай сырой материал (диктовку, документы, заметки, ссылки) без требования заполнить бриф.
Результат — один согласованный файл `presentation-blueprint.md`, который `pptx-strict`
использует как источник правды по содержанию.

**Граница со связанными скиллами (не нарушать):**
- `pres-blueprint` — что говорить, кому, в каком порядке и чем доказывать;
- `pptx-strict` — как дека выглядит и собирается (геометрия, токены, QA);
- `fact-checker-pro` — верификация утверждений со статусом «нужно проверить»;
- `deep-research` — если для каркаса не хватает данных, а не подтверждений.

Не начинай дизайн, не выбирай цвета и шрифты, не пиши код слайдов. Если пользователь
просит «сделай деку» с готовым содержанием — передай работу pptx-strict сразу.

## Рабочий процесс

### 1. Приём материала

Прими всё, что есть: диктовку, транскрипт, документы, таблицы, ссылки, прошлые деки,
ограничения показа. Правила приёма:

- Не заставляй пользователя повторять то, что уже есть в материалах.
- Отделяй авторские мысли от внешних фактов.
- Для каждого внешнего факта фиксируй источник или ставь статус `источник не предоставлен`.
- Не очищай разговорную речь слишком рано: сначала найди авторскую позицию и живые
  формулировки — они пойдут в action titles (§4 pptx-strict запрещает переписывать
  автора в безличный корпоративный язык).

### 2. Нужна ли презентация (ОБЯЗАТЕЛЬНО, не пропускать)

Проверь четыре альтернативы, прежде чем соглашаться делать деку:

| Альтернатива | Когда она лучше слайдов |
|---|---|
| Разговор без экрана | идея объясняется за 2–3 минуты голосом |
| Живое демо | продукт убедительнее показать, чем описывать |
| Документ (docx) | материал нелинейный, подробный, для самостоятельного чтения → doc-style |
| Письмо / сообщение | нужно одно решение от одного человека |

Презентация нужна, когда последовательность экранов ведёт человека от мысли к мысли:
сравнение вариантов, схема системы, динамика цифр, удержание хода рассказа.
Если альтернатива решает задачу лучше — скажи прямо и предложи её (для документа —
через doc-style). При пограничном случае предложи гибрид: короткий рассказ + демо +
несколько опорных экранов.

### 3. Формат

Значения по умолчанию:

- `PPTX` — показ на встрече, редактирование клиентом/командой, корпоративный шаблон,
  офлайн → производство в pptx-strict;
- `PDF` — неизменяемая версия для чтения и рассылки (экспорт из pptx-strict QA);
- `web presentation` — анимация, интерактив, калькулятор, единая ссылка
  (маршрут вне pptx-strict — согласовать инструмент отдельно);
- `live demo + опорные слайды` — гибрид;
- `document` — передать в doc-style.

Формат выбирается по условиям использования (кто смотрит, где, что делает после),
а не по моде. Зафиксируй основной формат и резервный.

### 4. Интервью (3–6 вопросов, по одному за раз)

Сначала извлеки ответы из материалов, затем спрашивай только то, без чего изменится
структура результата. Обязательно должно быть закрыто:

- кто принимает решение / слушает (роль, уровень, что уже знает);
- что происходит до и после показа;
- какая ОДНА мысль должна остаться у аудитории;
- какое действие или решение требуется после показа;
- какие утверждения потребуют доказательств;
- время показа и технические условия;
- кто владеет и редактирует материал после автора.

Если пользователь не знает ответа — предложи рабочую гипотезу и явно пометь её
`гипотеза`. Аудиторию и целевую эмоцию формулируй в терминах §19 pptx-strict
(банк/инвесткомитет → уверенность в возвратности; бенефициар → образ результата;
команда → сопричастность; клиент → выгода), чтобы производство приняло их без перевода.

### 5. Доказательный каркас

Сформулируй центральный тезис одним предложением без вводных конструкций.
Проверка: «Рынок AI» — тема, не тезис; «AI снижает стоимость проверки гипотез» — тезис.

Для каждого аргумента построй связку:

`утверждение → зачем оно аудитории → доказательство → источник → статус → место в рассказе`

Статусы (единые с fact-checker-pro):

- `подтверждено` — источник открыт и реально поддерживает утверждение;
- `нужно проверить` — источник назван, но не проверен → кандидат в fact-checker-pro;
- `рабочая гипотеза` — данных нет, принято как допущение;
- `авторское мнение` — позиция автора, доказательства не требует, но помечается.

ЗАПРЕЩЕНО: заполнять пробелы выдуманными числами, кейсами и цитатами; маскировать
слабое доказательство уверенным текстом. Слабое место — это риск, и оно фиксируется
как риск. Если утверждений со статусом «нужно проверить» три и больше — предложи
пользователю прогнать их через fact-checker-pro до сборки деки.

### 6. Маршрут

Используй 5 блоков §19 pptx-strict как каркас по умолчанию:

`контекст/завязка → проблема/напряжение → решение → доказательная база → вывод + действие`

Адаптируй под задачу: отчёт начинается с вывода; обучение — с проблемы и принципа;
клиентское предложение — с контекста клиента, а не с рассказа об авторе.
Опиши маршрут как 5–9 смысловых поворотов, а не как оформление слайдов.

Каждый будущий экран должен выполнять одну работу. Если экран не меняет понимание,
не даёт доказательство, не помогает навигации и не побуждает к действию — удали
или перенеси в приложение.

### 7. План экранов и карта визуализации

Для каждого экрана зафиксируй: работу экрана, главную мысль (заготовка action title,
≤ 60 знаков), материал, визуальную форму, что говорит автор.

Визуальную форму выбирай из каталога макетов §18 pptx-strict (задача → макет →
механика). Для сложных мест заполни карту визуализации: что требуется понять →
форма → почему она помогает → какие данные/ассеты нужны. Тест формы: «что зритель
поймёт быстрее благодаря ей?» Нет ответа — оставь простой текст.

В конце проверь разнообразие: длинная серия одинаковых текстовых экранов означает,
что смысловая работа не закончена.

### 8. Согласование и сохранение

Сначала покажи короткую версию (тезис, маршрут, спорные места) — дождись реакции.
После согласования сохрани полный `presentation-blueprint.md` по
[шаблону](references/blueprint-template.md) рядом с рабочими материалами проекта.

В блоке «Производство» укажи: целевой скилл (pptx-strict / doc-style / web),
бренд-профиль токен-слоя (neutral / gpbi / inache / architekton / pakgauz / другой)
и список утверждений, ожидающих fact-checker-pro. Дизайн не начинай — это работа
pptx-strict по явной просьбе пользователя.

## Gotchas

- Не начинай с количества слайдов: сначала определи работу презентации.
- Не путай тему с тезисом.
- Ссылка не подтверждает утверждение автоматически: проверяй, что источник
  действительно его поддерживает, либо ставь «нужно проверить».
- Не обещай интерактив в PPTX/PDF: конфликт формата фиксируй на шаге 3, а не в сборке.
- Не переписывай автора в безличный корпоративный язык.
- Blueprint без действия в финале — справка без адресата: действие + срок обязательны.
- Не дублируй работу pptx-strict: никаких цветов, шрифтов, макетных координат.

## Финальная проверка

- [ ] Решение «нужна / не нужна презентация» принято явно и обосновано.
- [ ] Формат выбран по условиям использования; резервный формат назван.
- [ ] Центральный тезис — одно предложение, повторяемое вслух.
- [ ] У каждого существенного утверждения есть статус; «нужно проверить» собраны
      списком для fact-checker-pro.
- [ ] Маршрут закрывает 5 блоков §19 и ведёт к действию со сроком.
- [ ] У каждого экрана одна работа и заготовка action title ≤ 60 знаков.
- [ ] Визуальные формы выбраны по задаче (§18), разнообразие проверено.
- [ ] Гипотезы и неясности помечены явно.
- [ ] Указаны целевой скилл производства и бренд-профиль токен-слоя.
