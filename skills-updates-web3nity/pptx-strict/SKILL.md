# PPTX Strict — Строгий деловой дизайн презентаций

Стандарт дизайна деловых презентаций в духе Bonnie&Slide. Все правила проверены на практике и оптимизированы для pptxgenjs.

> Перед началом работы ОБЯЗАТЕЛЬНО прочитай также основной pptx-скилл (`/skills/pptx/SKILL.md`) — он содержит техническую документацию по pptxgenjs, конвертацию, QA-процесс. Этот скилл дополняет его правилами дизайна.

## Как пользоваться скиллом — порядок работы

Разделы пронумерованы по мере накопления, но применять их следует в логическом порядке:

0. **Профиль (токен-слой).** Определить активный бренд-профиль по контексту запроса и
   загрузить его значения — см. «§0.1 Токен-слой: выбор профиля» ниже. Все дальнейшие
   пункты (палитра, шрифты) читают значения РОЛЕЙ из загруженного профиля.
1. **Замысел (что и кому).** §19 Нарратив деки → §0 пре-флайт «Дизайн-система прежде всего» → §17 Палитра.
2. **Выбор формы.** §18 Каталог макетов (что выбрать под мысль) → §4 Структура слайда.
3. **Вёрстка.** §1 Сетка → §1.1 Бюджет → §1.2 Принципы композиции → §2 Типографика → §3 Цвет → §5 Компоненты → §6 Диаграммы → §7 Таблицы → §8–§11 спец-слайды → §16 Изображения.
4. **Бренд-модуль** (дека «Иначе»): §15 — переопределяет общие правила §3/§5/§7.
5. **Контроль.** §13 QA-чеклист → шаг валидатора токенов → §13.1 Critic-gate → §14 Антипаттерны.
6. **Справка.** §12 Русская типографика, §20 Глоссарий.

Сквозной принцип всех разделов: **одна идея на слайд, одна доминанта, одна дизайн-система на деку.**

## 0.1 Токен-слой: выбор профиля (ОБЯЗАТЕЛЬНО, выполнить первым)

Цвета и шрифты деки — не хардкод в этом файле, а РОЛИ, значения которых лежат в
`tokens/<профиль>.json` (полная схема ролей и наследования — `tokens/schema.md`).

**Разрешение профиля по контексту запроса:**

| Контекст запроса | Профиль |
|---|---|
| «для ГПБИ», упоминание Газпромбанк-Инвест | `gpbi` |
| «Архитектон», личный контур пользователя | `architekton` |
| «Иначе» | `inache` |
| «Пакгауз» | `pakgauz` |
| контекст не указан / не распознан | `neutral` |

**Путь к токенам** (в порядке приоритета):
1. `C:\claude-skills\tokens\<профиль>.json` — основной путь (Claude Code, есть доступ к репозиторию).
2. Если недоступен (среда claude.ai) — `references/tokens/<профиль>.json` внутри самого скилла.

**Загрузка:** прочитать JSON профиля; если задан `"inherits"` — прочитать родителя и
слить рекурсивно (потомок поверх родителя, по ключам, не по секциям целиком — см.
`tokens/schema.md`, «Наследование»). Дальше по тексту скилла роли вида `palette.accent.primary`,
`typography.pptx.roles.display` читаются из результата слияния для активного профиля.

Профиль фиксируется на всю деку — не переключать посреди сборки.

## 0. Выбор стратегии: правка vs пересборка (КРИТИЧЕСКИ ВАЖНО)

Перед началом работы определить стратегию. Неправильный выбор приводит к деградации качества.

### Точечная правка через python-pptx (ПРИОРИТЕТ при наличии исходника)

Использовать если:
- Исходник уже визуально сбалансирован (собран вручную или профессиональным инструментом)
- Нужны технические исправления (шрифты < 10pt, добавление callout, вставка section dividers)
- Есть диаграммы, таблицы, сложная вёрстка — их дорого воспроизводить
- Цветовая палитра индивидуальная (семантические цвета суббрендов, конкурентов)

Что делать: `Presentation(src) → fix_fonts() → add_callouts() → add_dividers() → save(dst)`

### Пересборка в pptxgenjs (с нуля)

Использовать если:
- Исходника нет — создание по ТЗ / документу / данным
- Исходник визуально плохой (нет сетки, хаотичная вёрстка, несистемный дизайн)
- Нужна радикальная реструктуризация (другой storyline, другая логика разделов)

### Антипаттерн: пересборка профессиональной деки ради метрик

Пересобирать с нуля деку, которая визуально хороша, но имеет технические дефекты (шрифт 8.5pt, нет callout) — **ЗАПРЕЩЕНО**. Это как перепечатывать книгу ради опечаток: опечатки уйдут, но уйдёт авторская вёрстка. Правильный путь — точечная правка: `run.font.size = max(run.font.size, Pt(10))`.


### Fallback при ограничениях инструментов

При редактировании через Office.js / python-pptx могут быть ограничения:
- Некоторые API (getSelectedSlides, textFrame, edit_slide_xml) могут быть недоступны
- Диаграммы (charts) не редактируются через python-pptx напрямую — только через XML

**Fallback-план:**
1. Позиционировать фигуры через доступный API (left/top/width/height)
2. Если форматирование текста (шрифт, anchor, цвет) недоступно — **предупредить пользователя**, что нужна ручная доводка
3. **Не обещать то, что нельзя сделать** — лучше честно сказать «шрифт нужно поправить вручную», чем молча сгенерировать сломанный файл


### Чеклист: что теряется при пересборке

- Индивидуальная настройка координат каждого элемента
- Семантическая цветовая палитра (6+ цветов с привязкой к сущностям)
- Качество рендера оригинальных диаграмм (python-pptx charts ≠ pptxgenjs charts)
- Пропорции таблиц (ширина столбцов, высота строк)
- Данные (!): при пересборке легко потерять строки таблиц, сегменты диаграмм

### Дизайн-система прежде всего (пре-флайт)
До первого слайда зафиксировать дизайн-систему — и дальше строить всё внутри неё:
- **Палитра**: 2 базовых цвета + 1 акцент (как собрать — §17; запись — §3).
- **Шрифты**: один или осознанная пара заголовок/текст (§2).
- **Геометрия углов**: прямые ИЛИ скруглённые с единым абсолютным радиусом (например, R = 6pt) — один выбор на всю деку. При скруглениях радиус обязательно нормируется через adjustment (§5.1), иначе плашки разного размера получат визуально разные радиусы.
- **Иконки**: один стиль и набор (§1.2 «Единый стиль иконок»).
- **Визуальный мотив**: один повторяющийся элемент (форма буллета, акцентная плашка, паттерн) — для узнаваемости (§1.2, принцип 7).

Лучшие деки — это система, а не набор красивых слайдов поодиночке. Меняешь систему — один раз для всей деки.

## 1. Формат и сетка

- **Формат**: 16:9 (LAYOUT_16x9), 10" × 5.625"
- **Поля**: минимум 0.5" от краёв слайда для любого контента (сверху и по бокам; снизу действует канон зон ниже)
- **Зазоры между элементами**: минимум 0.3" (лучше 0.4")

### 1.0 Геометрия листа — фиксированные зоны (ЕДИНЫ для всей деки, ОБЯЗАТЕЛЬНО)

Зоны задаются один раз на деку и НЕ меняются от слайда к слайду. Меняется контент — не сетка.

| Зона | Координаты (дюймы) | Что в ней |
|---|---|---|
| Поля слева/справа | контент в x: 0.7–9.3 (рабочая ширина 8.6") | весь контент |
| Шапка | y: 0.4–1.5 | метка секции, акцентная линия, заголовок |
| Зона контента | y: 1.5–4.7 | карточки, диаграммы, таблицы, callout |
| Футер-строка | y = 4.85, h = 0.25 (низ = 5.10) | номер слайда (справа) — всегда; источник/сноска (слева) — если есть |
| Запретная зона | y > 5.10 | всегда пусто |

Нижнее поле листа (от 5.10 до края = 0.525" ≈ 13 мм) равно боковым полям — строка стоит «в листе», а не прилипает к обрезу. Значение утверждено пользователем 2026-06-12 после двух итераций — НЕ уменьшать.

**Жёсткие правила:**
- Любой контент (включая callout): `y + h ≤ 4.7"`. Единственное, что ниже — футер-строка.
- Футер-строка одна и та же на всех слайдах: одинаковые y, h, fontSize. Источник и номер сидят на **одной базовой линии** — источник НИКОГДА не оказывается ниже номера слайда.
- Ни один объект не пересекает 5.10" — это нижний предел текста на листе.
- Исключения из канона: титульный, финальный и section dividers (без шапки и футера) и full-bleed-изображения/фоновые формы (§16, «breaking the frame» — только графика, не текст).

**Направляющие в файле (ОБЯЗАТЕЛЬНО при генерации .pptx)** — зашивать канон в `ppt/viewProps.xml`: границы видны при ручной правке в PowerPoint, на показ и печать не влияют. Горизонтали: 1.5" (начало контента), 4.7" (конец контента), 4.85" (верх футера), 5.10" (нижний предел текста); вертикали: 0.7" и 9.3". Пост-пасс после сохранения файла:

```python
import zipfile, re, os

def add_canon_guides(path):
    """Направляющие канона §1.0 в viewProps.xml (pos в 1/8 pt: дюймы × 576)."""
    e8 = lambda inch: round(inch * 576)
    g = ('<p:guideLst>'
         + ''.join(f'<p:guide orient="horz" pos="{e8(y)}"/>' for y in (1.5, 4.7, 4.85, 5.10))
         + ''.join(f'<p:guide pos="{e8(x)}"/>' for x in (0.7, 9.3))
         + '</p:guideLst>')
    tmp = path + '.tmp'
    with zipfile.ZipFile(path) as zin:
        vp = zin.read('ppt/viewProps.xml').decode('utf-8')
        vp = re.sub(r'<p:guideLst>.*?</p:guideLst>|<p:guideLst/>', '', vp, flags=re.S)
        vp = re.sub(r'(</p:cViewPr>)', r'\1' + g, vp, count=1)
        vp = re.sub(r'<p:cSldViewPr(?![^>]*showGuides)', '<p:cSldViewPr showGuides="1"', vp, count=1)
        with zipfile.ZipFile(tmp, 'w', zipfile.ZIP_DEFLATED) as zout:
            for n in zin.namelist():
                zout.writestr(n, vp.encode('utf-8') if n == 'ppt/viewProps.xml' else zin.read(n))
    os.replace(tmp, path)
```

- **Выравнивание**: все однотипные элементы строго на одной линии (x или y)
- **Одна идея на слайд** — если хочется добавить ещё, это повод для нового слайда
- **Максимум 5–7 объектов или групп** на слайде — перегруженный слайд не читается

## 1.1 Вертикальный бюджет контента (ОБЯЗАТЕЛЬНО)

Доступная высота под контент на стандартном слайде (зоны — §1.0):

```
Слайд:           5.625"
Шапка:           0.4–1.5"
Зона контента:   1.5–4.7"  → 3.2"
− Callout:       0.45"  (вывод «so what» у нижней границы контента)
─────────────────────
= Бюджет:        ≈ 2.75"
Футер-строка:    y=4.85, h=0.25  (источник + номер, вне зоны контента)
```

**Формула**: `Σ(element_h + gap) ≤ 2.75"` — считать ДО написания кода.

Для N повторяющихся элементов (строки таблицы, карточки, пункты TOC): `step = budget / N`. Если `step < 0.3"` — контент не поместится, разбить на два слайда.

**Жёсткое правило**: ни один элемент контента не должен иметь `y + h > 4.7"`. Ниже — только футер-строка (y=4.85, h=0.25), и ничто не пересекает 5.10".


### Правило «сначала замерь, потом размести» (при добавлении элементов на существующий слайд)

Перед добавлением callout «so what» на существующий слайд — программно найти нижнюю границу контента:

```python
max_bottom = max((sh.top + sh.height) / 914400 for sh in slide.shapes)
```

Если `max_bottom > 4.05"` — на слайде **нет места для callout** стандартного размера. Варианты (в порядке приоритета):
1. Вынести вывод в заголовок слайда (переформулировать как action title)
2. Сместить контент вверх на 0.3–0.4" (если есть воздух между шапкой и данными)
3. Уменьшить callout до 1 строки (h=0.3", fontSize: 10)
4. Разбить слайд на два
5. Добавить как speaker note (крайний случай — зритель не увидит)

**ЗАПРЕЩЕНО**: размещать callout «вслепую» на фиксированной y-координате без проверки свободного места.


### Вертикальное распределение: сначала макет, потом детали (ОБЯЗАТЕЛЬНО)

При создании или правке слайда — **всегда пересчитывать всю вертикальную раскладку целиком**, от заголовка до callout-бара. Нельзя двигать один элемент на 4pt — это создаёт каскадные проблемы.

**Алгоритм вертикальной раскладки:**
1. Определить фиксированные зоны: шапка (y: 0.4–1.5"), callout (снизу), источник
2. Определить высоту callout по количеству строк (1 строка = h 0.3", 2 строки = h ≥ 0.4")
3. `calloutTop = slideHeight - calloutHeight - bottomMargin`
4. `availableHeight = calloutTop - contentStart`
5. Распределить контент в `availableHeight` с **равномерными зазорами**

**Антипаттерн**: зазор между блоком A и B = 4pt, а между B и C = 22pt. Зазоры между логическими блоками (заголовок → карточки → секция контекста → callout) должны быть **пропорциональны** — не обязательно одинаковы, но визуально сбалансированы.

**Метод**: `свободное_место = availableHeight - Σ(высот_блоков)`. Раздать `свободное_место` равномерно между зазорами.

## 1.2 Принципы композиции слайда

Семь принципов, обязательных при компоновке каждого слайда:

1. **Баланс** — гармоничное распределение визуального «веса». Слайд не должен «заваливаться» на одну сторону. Использовать сетки: правило третей, золотое сечение (1:1.618), симметричное деление.
2. **Контраст** — разница по размеру, цвету, толщине. Контраст управляет вниманием и упрощает чтение. Заголовок — крупный bold, текст — тонкий regular.
3. **Доминанта** — на слайде должен быть один главный объект, считываемый первым. Ничего не должно спорить с доминантой. Если всё одного размера — доминанты нет, взгляд «плавает».
4. **Выравнивание** — объекты на одной линии воспринимаются как группа. Невыровненные элементы создают визуальный хаос. Все однотипные элементы — строго по сетке.
5. **Ограничение** — не более 5–7 объектов / групп на слайде, не более 2 семейств шрифтов, не более 3–4 цветов, минимум декоративных эффектов. Перегруженный слайд хуже пустого.
6. **Близость (Proximity)** — связанные элементы рядом, несвязанные разделены воздухом. Группировка по близости создаёт смысловые блоки без рамок и подписей. Подпись стоит вплотную к своему объекту, а не на равном расстоянии от двух.
7. **Повторение и единообразие (Repetition / Consistency)** — один визуальный паттерн на всю деку: шрифт заголовка, цвет акцента, стиль иконок, отступы шапки, углы, логика макетов. Повторение даёт связность, разнобой читается как любительство. Единообразие шире повторения — это единые правила на уровне всего файла.

### Виды контраста
Контраст (принцип 2) работает по шести осям — комбинировать, но не все сразу:
- **Размер** — заголовок крупнее текста, ключевая цифра огромная.
- **Форма** — острые углы против плавных, прямоугольный блок против тонкой линии.
- **Цвет** — акцент против нейтрали; противоположные на круге (§17).
- **Тон** — светло-серый против тёмно-серого: контраст без агрессии цвета.
- **Текстура** — фото против плоской заливки, заполненное против контурного.
- **Расстояние** — элемент в «воздухе» против плотной группы (принцип 6, Близость).

Без контраста хотя бы по одной оси доминанты нет (принцип 3).

### Визуальная иерархия считывания

Аудитория считывает слайд в предсказуемом порядке: крупный заголовок → выделенный цветом подзаголовок → основной контент → сноски. Дизайн должен усиливать этот порядок, а не бороться с ним.

### Bento-дизайн (карточная вёрстка)

Вместо длинных списков с буллитами — модульная карточная вёрстка: каждый пункт в отдельном блоке с иконкой/номером, заголовком и кратким пояснением. Ключевые слова подсвечены акцентным цветом. Буллит-листы — антипаттерн для деловых презентаций.

### Единый стиль иконок
Все иконки в деке — **одного стиля и одного набора**: либо все outline (контурные), либо все filled (залитые), не смешивать; 3D-иконки не использовать. Outline легче и современнее — подходит для большинства строгих дек. Размер и толщина линий иконок единые. Смешение наборов (одни контурные, другие залитые) — типичная любительская ошибка (нарушение принципа 7).

### Белое пространство — инструмент, а не дыра
Воздух вокруг элемента — рабочий инструмент: даёт деке дышать, выделяет доминанту, облегчает чтение. Различать:
- **Осознанный воздух** — равномерные поля, «рамка тишины» вокруг ключевого элемента → оставлять.
- **Случайная дыра** — пустая нижняя треть под таблицей, провал между блоками (§7) → заполнять callout'ом или перекомпоновкой.

Критерий: воздух симметричен и работает на доминанту — инструмент; воздух односторонний и случайный — недоработка.

### Визуальные метафоры
Абстрактную идею перевести в конкретный образ: рост → лестница/гора, связь → сеть/мост, скорость → стрелка/молния, этапы → дорога. Делает мысль запоминаемой. В строгой деке — **дозированно**: метафора уместна на разделителе, обложке, концептуальном слайде; на data-слайде она не подменяет график. Один образ — одна идея.

### Нарушать правила — осознанно
Любое правило скилла можно нарушить, но только понимая зачем. Нарушение по незнанию — ошибка; по расчёту — приём. Отступление от стандарта должно читаться как намеренное решение, а не как недосмотр.

## 2. Типографика

### Шрифт
- **Базовый принцип**: одно шрифтовое суперсемейство закрывает всю презентацию. Это безопасный дефолт — использовать его, когда брендбука нет и шрифтовая пара не задана.
- **Стандарт деки — семейство роли `typography.pptx.primary` активного профиля** (§0.1; в `neutral` — Aptos). Роли внутри семейства фиксированы (кегли — часть конструкции скилла, не меняются от профиля; источник гарнитуры для каждой роли — `typography.pptx.roles.*` профиля):

| Роль | fontFace (роль профиля) | Кегль |
|---|---|---|
| Заголовок слайда (H1), заголовок титула | `roles.display`, bold | 22–28 / 36–42pt |
| KPI «цифра-герой», номер раздела на divider | `roles.display`, bold | 36–96pt |
| Подзаголовок секции | `roles.semibold` | 18pt |
| Метка секции (CAPS, charSpacing 3) | `roles.semibold` | 11–12pt |
| Основной текст | `primary` | 13–14pt |
| Карточки, callout (акценты — bold) | `primary` | 11–12pt |
| Таблицы: шапка | `roles.semibold` | 10–11pt (14pt в §15) |
| Таблицы: ячейки | `primary` | 10–11pt |
| Диаграммы: оси, data labels, легенда | `primary` | 10–11pt |
| Источник/сноска, номер слайда (футер, §1.0) | `primary` | 10pt |
| Цитата на цитатном слайде (осознанный приём) | `roles.serif`, italic | 24–32pt |
| Длинные подписи в узких местах (дозированно) | `roles.narrow` | по месту, ≥ 10pt |
| Mono-роль (если есть в профиле) | в деках не используется (только код/идентификаторы) | — |

- **Правило Display**: `roles.display` — только на кеглях ≥ 20pt (скроен под крупные размеры); ниже 20pt — `primary`. Не смешивать `roles.display` и `primary` на одном уровне иерархии.
- **Техника**: в PowerPoint/pptxgenjs `bold: true` переключает пару Regular↔Bold; промежуточные насыщенности — отдельные имена fontFace (роли `roles.semibold` и т.п. профиля, напр. «Aptos SemiBold»).
- **Fallback-цепочка (пре-флайт, ОБЯЗАТЕЛЬНО)**: перед сборкой проверить наличие гарнитуры в системе; брать первую доступную из `typography.pptx.fallback` активного профиля, начиная с `primary` (в `neutral`: **Aptos → Roboto → Inter → Montserrat → Calibri**). Проверка:

```powershell
Add-Type -AssemblyName PresentationCore
$have = [Windows.Media.Fonts]::SystemFontFamilies | ForEach-Object { $_.Source }
$chain = @($profile.typography.pptx.primary) + $profile.typography.pptx.fallback  # из tokens/<профиль>.json
$chain | Where-Object { $have -contains $_ } | Select-Object -First 1
```

  При fallback вся ролевая таблица переносится на одну гарнитуру: заголовки — она же bold (Display-гарнитуры у заменителей нет), Narrow → Roboto Condensed (только для Roboto) либо базовое начертание, Serif-цитата → курсив базовой. Выбранная гарнитура фиксируется на всю деку и указывается в заметках к файлу, если это не первая в цепочке профиля (у получателя без неё PowerPoint молча подставит замену).

### Брендовые шрифты: имя берётся из ФАЙЛА шрифта, не из брендбука (ОБЯЗАТЕЛЬНО)

Урок кейса «Cera CY» (ГПБ, 06.2026): брендбук называл шрифт «Cera CY», лицензионные файлы группы несли семейство **«Cera Pro»** — дека, прописанная по имени из брендбука, молча рендерилась Calibri, и три раунда «починки XML» ничего не меняли, потому что XML был исправен. Правила:

1. **Источник истины — name-таблица файла шрифта** (nameID 16, иначе 1), а не маркетинговое имя из брендбука/гайда. Проверка: Add-Type -AssemblyName PresentationCore; (New-Object Windows.Media.GlyphTypeface(путь к .otf)).Win32FamilyNames — прописывать в деку ровно это имя.
2. **Панель шрифтов PowerPoint — НЕ доказательство.** При клике на фигуру панель показывает запрошенное в XML имя, а не фактически отрисованный шрифт. Единственная проверка рендера — экспорт слайда в PNG и взгляд на начертание.
3. **Диагностика «XML правильный, а выглядит как Calibri»**: причина всегда в системе, а не в разметке — шрифт не установлен ЛИБО установлен под другим именем. Порядок проверки: сначала реестр/DirectWrite (HKCU + HKLM; GDI+ не видит пользовательские шрифты), потом name-таблица файла, и только потом XML. Не наоборот.
4. **Смена шрифта существующей деки = три слоя**: <a:latin> в runs + <a:endParaRPr> (иначе каретка и панель показывают старый шрифт, и новый текст набирается им) + theme1.xml major/minorFont. Заменить только runs — источник ложных «не сработало».
5. **CFF/OTF не встраивается**: PowerPoint умеет embed только TrueType-outlines; лицензионные OTF (PostScript-флейвор, как Cera Pro) во вложение не уходят — у внешнего получателя будет подмена. Для отправки наружу с брендовым OTF-шрифтом — обязательно PDF рядом с pptx.
6. Установка пользовательских шрифтов без админ-прав: файл в %LOCALAPPDATA%\\Microsoft\\Windows\\Fonts + значение в HKCU Fonts («Full Name (OpenType)» → полный путь), затем перезапуск PowerPoint.
- **Пара из двух шрифтов допустима**, когда работаем в брендбуке (клиента или собственном) с заранее определённой парой, либо как осознанный приём. Тогда: один шрифт — заголовки/акценты, второй — основной текст. **Не больше двух семейств.**
- Пару подбирать **по сходству** (одно суперсемейство: Roboto + Roboto Slab, IBM Plex Sans + IBM Plex Serif) или **по контрасту** (антиква-заголовок + гротеск-текст: Playfair Display + Inter). Контраст должен быть **заметным** — два похожих, но разных гротеска читаются как ошибка, а не как приём.
- **Иерархия всё равно строится размером и насыщенностью**, а не сменой гарнитуры внутри одного уровня. Два шрифта = два уровня (заголовок / текст), а не декорация. Внутри одного уровня — одна гарнитура.
- **Основной текст** — только читаемый шрифт (антиква или гротеск). Скрипт / акцидентный / декоративный шрифт — **только** в крупном заголовке или на обложке, никогда в body.
- **Без брендбука и без заданной пары — один шрифт.** Не выдумывать вторую гарнитуру ради разнообразия.
- Если шрифт не установлен у пользователя — PowerPoint подставит fallback. Для нестандартной пары указать нужные шрифты в заметках к файлу.

### Размеры (минимумы — жёсткие, не нарушать)
| Элемент | Минимум | Рекомендуемый |
|---------|---------|---------------|
| Заголовок слайда (H1) | 20 pt | 22–28 pt |
| Подзаголовок секции | 16 pt | 18 pt |
| Метка секции (категория вверху) | 11 pt | 11–12 pt, CAPS, charSpacing: 3 |
| Основной текст | 12 pt | 13–14 pt |
| Текст в карточках/callout | 10 pt | 11–12 pt |
| Подписи к таблицам/диаграммам | 10 pt | 10–11 pt |
| Текст в ячейках таблиц | 10 pt | 10–11 pt |
| Подписи осей диаграмм | 10 pt | 10–11 pt |
| Data labels диаграмм | 10 pt | 10–11 pt |
| Легенда диаграмм | 10 pt | 10 pt |
| Источник/сноска | 10 pt | 10 pt |
| **Абсолютный минимум** | **10 pt** | — |

**ЗАПРЕЩЕНО**: любой текст меньше 10 pt. Если не влезает — сокращай текст, не шрифт.


### Длина заголовка (action title)

Action title должен умещаться в **одну строку** при fontSize 22pt и ширине 8.6". Это примерно **50–60 символов** для кириллицы в Aptos Display / Roboto.

- ✅ «Рынок растёт на 8–12% при 4–9× отставании от Европы» (51 знак)
- ❌ «Малевичъ — единственный бренд с digital-преимуществом при контрактной модели» (78 знаков → перенос)

Перенос заголовка на 2 строки **съедает 0.5" вертикального бюджета** и ломает визуальную иерархию. Если мысль не влезает в 60 символов — сократить, не терпеть перенос.

### Иерархия
- Заголовки — bold, цвет `dark`
- Метки секций — CAPS, charSpacing: 2–3, цвет `muted`, bold
- Основной текст — regular, цвет `body`
- Акцентный текст — bold или цвет `accent`

## 3. Цветовая палитра

Строгая палитра из 6–8 цветов — значения берутся из ролей активного профиля (§0.1),
не хардкодятся. Объект `C` в коде собирается из профиля, а не вписывается константами:

```javascript
// C собирается из tokens/<профиль>.json (после разворачивания inherits) —
// пример конкретных значений ниже даёт профиль neutral, но в коде не хардкодить,
// а читать поля профиля.
const C = {
  dark:      profile.palette.text.heading,      // заголовки, тёмные фоны (neutral: 1A1A1A)
  accent:    profile.palette.accent.primary,    // основной акцент CTA/выделение (neutral: 1F3A5F)
  accent2:   profile.palette.accent.secondary,  // вторичный акцент (neutral: 2C3E50)
  body:      profile.palette.text.body_screen,  // основной текст (neutral: 262626)
  muted:     profile.palette.text.muted,        // подписи, сноски (neutral: 808080)
  light:     profile.palette.fills.callout,     // фон карточек (neutral: F5F5F5)
  white:     profile.palette.text.inverse,      // фон слайдов (neutral: FFFFFF)
  border:    profile.palette.lines.row,         // линии, разделители (neutral: D9D9D9)
  highlight: profile.palette.fills.key_input,   // подсветка в таблицах (роль key_input)
};
```

### Правила цвета
- **Фон слайдов**: белый (`palette.text.inverse`) — основной; тёмный (`C.dark`) — только титульный и финальный
- **Акцент на тёмном фоне** (титул, финал, section divider): брать роль `palette.accent.on_dark` активного профиля, если она задана (акцент, читаемый на тёмном). Если роль не задана (напр. `neutral`) — акцентная линия/подзаголовок на тёмном фоне берут `palette.text.inverse` (белый), потому что основной `accent.primary` на тёмном фоне часто нечитаем (тёмный на тёмном). НЕ ставить `accent.primary` на тёмный фон вслепую.
- **Максимум 2 акцентных цвета** на презентацию (`accent` + `accent2` профиля)
- **Highlight бренда**: заливка роли `palette.fills.key_input` + акцентный текст роли `palette.accent.primary` для выделения в таблицах
- **Контраст**: тёмный текст на светлом фоне, светлый текст на тёмном фоне. Никогда серый на сером


### Семантические цвета (исключение из правила «максимум 2 акцента»)

«Максимум 2 акцентных цвета» относится к **функциональным акцентам** (CTA, highlight, выделение строки). Но **семантические цвета** — это другое:
- Каждый суббренд в портфеле — свой цвет (GrafArt — красный, Tician — бирюзовый, Monet — оранжевый)
- Каждый квадрант SWOT — свой цвет (S — зелёный, W — красный, O — синий, T — оранжевый)
- Каждый конкурент в матрице позиционирования — свой цвет

Семантические цвета **несут информацию** — их нельзя унифицировать до 2. При правке или пересборке деки — **сохранять семантическую палитру оригинала**. Потеря семантических цветов = потеря визуальной идентичности сущностей.

## 4. Структура слайда

### Правило «So What» (где данные несут нетривиальный вывод)
Слайд с данными (диаграмма, таблица, цифры) снабжается callout-выводом, КОГДА вывод нетривиален — зритель не должен сам догадываться, что означают данные. Callout не самоцель: если вывод самоочевиден из визуала, либо слайд концептуальный/структурный (section divider, цитата, триптих, нумерованный список, схема-процесс) и числового «so what» нет — callout НЕ добавлять; пустую плашку ради канона не ставить (пустой или тавтологичный callout — сам по себе антипаттерн). Формат (когда уместен): callout-блок с акцентной боковой полоской внизу или справа от данных. Текст вывода — 1–2 предложения, начинающиеся с действия или следствия для бизнеса. Пример: не «маркеры +45%», а «Маркеры — самая быстрорастущая категория: все три топ-позиции представлены в ассортименте Малевичъ».

### Приём «понижение заголовка» (правка чужой деки)

При точечной правке (§0) чужой деки со старым описательным заголовком («Итоги запуска новой рекламной кампании», «Доля рекламного рынка по каналам (%)») — заголовок НЕ удаляется. Порядок:
1. Старый заголовок переносится вниз и становится подзаголовком (копировать текст, не форматирование — стиль применится от нового места).
2. Сверху пишется новый короткий заголовок-вывод (action title, §2 «Длина заголовка»): не тема, а результат. Пример: «Итоги запуска новой рекламной кампании» → подзаголовок; сверху — «Бьём итоги по охвату». Второй пример из того же приёма: «Доля рекламного рынка по каналам (%)» → подзаголовок/подпись графика; заголовок слайда — «Рынок digital рекламы обгоняет ТВ».
3. Иерархия весом: новый заголовок — жирнее и/или крупнее старого (который теперь подзаголовок), а не наоборот.

Смысл приёма — сохранить исходную формулировку (в ней часто точная тема/метрика) и добавить над ней вывод, вместо того чтобы придумывать заголовок с нуля или терять описательный текст. Источник: курс Bonnie&Slide, `tokens/_pptx-course-extracts/slajdy-u2-zapomnyat.md`.

### Section Dividers (разбивочные слайды)
При количестве слайдов > 12 ОБЯЗАТЕЛЬНО вставлять section dividers между крупными разделами презентации. Формат: тёмный или акцентный фон, номер раздела крупно (48–56pt, accent color), название раздела (24–28pt, white), без шапки и источника. Цель — визуальная «передышка» и навигация. Минимум 2 section divider на деку из 15+ слайдов.

### Шапка (одинаковая на всех слайдах, кроме титульного, финального и section dividers)
```
y=0.4  МЕТКА СЕКЦИИ  (11pt, CAPS, muted, charSpacing: 3)
y=0.85 ─── акцентная линия (0.8" шириной, 0.04" высотой, accent color)
y=1.0  Заголовок слайда  (20–28pt, bold, dark)
```

### Футер-строка: источник/сноска + номер слайда (единая на всех слайдах, §1.0)

Один горизонтальный ряд внизу с общими y и h — источник и номер на одной базовой линии:

```javascript
// Источник/сноска — слева
s.addText(sourceText, { x: 0.7, y: 4.85, w: 8.4, h: 0.25, fontSize: 10, color: C.muted, align: "left", valign: "middle" });
// Номер слайда — справа
s.addText(String(pageNum), { x: 9.1, y: 4.85, w: 0.4, h: 0.25, fontSize: 10, color: C.muted, align: "right", valign: "middle" });
```

**Правила:**
- **Источник/сноска — опциональна**: рисуется, только когда есть реальный источник данных или сноска. Нет источника (внутренние тезисные слайды, специмен/каталог, слайд без данных) → футер = только номер слайда справа; левый текст не выводить (не ставить туда название файла/деки ради заполнения). Номер слайда — всегда.
- Источник/сноска — строго **одна строка** (≈ 110–120 знаков при 10pt на ширине 8.4"). Длиннее — сократить текст, а не переносить на вторую строку и не опускать ниже.
- y, h, fontSize футера **не меняются от слайда к слайду** — футер стоит на одном месте по всей деке.
- ЗАПРЕЩЕНО: источник ниже номера слайда; «гуляющий» по слайдам футер; любой текст с низом ниже 5.10".

## 5. Компоненты дизайна

### 5.1 Углы карточек: единый радиус через нормировку adjustment

Геометрия углов — параметр дизайн-системы (§0 пре-флайт): либо прямые (`rect`) везде, либо скруглённые (`roundRect`) везде с **одним абсолютным радиусом**. Смешение в одной деке — дефект.

**Почему «одинаковые» скругления получаются разными.** В OOXML радиус `roundRect` хранится не в pt, а как adjustment-значение — доля от **меньшей стороны фигуры** (adj 0…50000 = 0–50%):

```
радиус_визуальный = adj / 100000 × min(w, h)
```

Одинаковый adj (или дефолтные 16667) на широкой плашке диаграммы и узкой KPI-плашке даёт разные визуальные радиусы. Поэтому adj считается **для каждой фигуры отдельно** под фиксированный абсолютный радиус:

```
adj = R / min(w, h) × 100000
```

**Канонический способ — пост-пасс python-pptx** (детерминирован, не зависит от версии генератора):

```python
from pptx.util import Pt

def set_corner_radius(shape, radius_pt=6):
    """Одинаковый абсолютный радиус скругления для фигур любого размера.
    Применять ко всем roundRect-фигурам деки одним проходом."""
    shape.adjustments[0] = Pt(radius_pt) / min(shape.width, shape.height)
```

**pptxgenjs**: у `ROUNDED_RECTANGLE` есть `rectRadius` (в дюймах, абсолютный) — свежие версии сами пересчитывают его в adj под размер фигуры. Поведение `rectRadius` между версиями менялось, поэтому после генерации обязательна визуальная проверка радиусов на разноразмерных плашках; при расхождении — пост-пасс `set_corner_radius()` по всему файлу.

**Правила:**
- Один радиус на всю деку (рекомендуемый диапазон 4–8pt; 6pt — дефолт). Радиус — часть дизайн-системы, фиксируется до вёрстки.

**Референс ГПБ (брендбук «Визуальные константы Газпромбанка», 2024 V1):**
- Скругление плашек («динамический остров» и производные) — **20 Figma-px ≈ 5,3 мм на А4-макете**. Промер четырёх плашек брендбука разной ширины (456–868 px растра) подтверждает: радиус **абсолютный и одинаковый** на всех плашках (≈22 px растра везде) — тот же принцип нормировки, что в этом разделе.
- Эквивалент для слайда 960×540pt (перенос по высоте А4 297 мм → слайд 190,5 мм): 5,3 × 0,64 ≈ 3,4 мм = **R ≈ 10pt**. Для дек в бренде ГПБ использовать R = 10pt.
- Капсульные пилюли (теги, навигация, бейджи в стиле брендбука) — полное скругление: `adj = 50000` (радиус = ½ высоты), на размер не нормируются.
- В бренде ГПБ допускаются фирменные градиенты на плашках (Sapphire–Azurite и типовые пары брендбука) — переопределяет общий запрет градиентов; вне ГПБ-бренда запрет действует.
- Радиус не должен «съедать» фигуру: для тонких элементов (акцентные полоски, линии) скругление не применяется — они остаются `rect`.
- Акцентная полоска поверх скруглённой карточки: либо вписана с отступом от угла, либо карточка получает полоску через левую/верхнюю границу цветом (border), а не отдельной фигурой, перекрывающей радиус.
- QA: на рендере сравнить углы самой большой и самой маленькой плашки слайда — визуально идентичны.

### Составная плашка: встройка (боковая полоса, шапка-кап, цветная зона)

Встройку, касающуюся углов скруглённой карточки, НЕЛЬЗЯ рисовать отдельным roundRect впритык к краю: её углы не совпадут с карточкой. Две причины: (а) свои четыре угла встройки скругляются и внутри карточки — читается как отдельная «пилюля»; (б) тонкая полоса физически не может нести радиус карточки — максимум радиуса roundRect = ½ её меньшей стороны (полоса 4pt → максимум 2pt при R карточки 6pt).

**Паттерн «маска»** — слитная встройка из четырёх слоёв (снизу вверх):
1. **Карточка** roundRect: заливка, тень; как обычно.
2. **Встройка** roundRect **тем же R**, что у карточки, увеличенная вглубь карточки так, чтобы её min(w, h) ≥ 2R: при видимой толщине t габарит = max(2R, t + R). Прижата к краю карточки, adj нормирован под новый габарит, без собственной границы.
3. **Маска** — прямоугольник цветом заливки карточки, закрывающий внутреннюю (лишнюю) часть встройки **с перекрытием 2pt** вглубь — без перекрытия антиалиасинг даёт волосяную линию по кромке.
4. **Рамка-контур** roundRect поверх: noFill, линия карточки, точные габариты карточки — восстанавливает границу над встройкой и маской.

Текст кладётся выше всех четырёх слоёв. Ограничение: заливка карточки должна быть однотонной (маска невидима только на ровном фоне) — в строгой деке это всегда так.

**Альтернатива** для встроек габаритом ≥ R: пресет `round2SameRect` (adj1 = R-нормировка для пары углов у края, adj2 = 0) — без маски, но скругляет только два смежных верхних угла; для боковых встроек требует поворота фигуры или custGeom.

**Третий вариант** — встройка, не касающаяся углов: обычный rect с отступом от угла ≥ R, читается как осознанный внутренний элемент.

### Детект и исправление составных плашек (точечная правка существующих дек)

Правила выверены на боевом файле двусторонней проверкой (генератор python-pptx ↔ независимый аудит Claude in PowerPoint).

**Детект пары «карточка + встройка» (строгие определения):**
- Карточка-кандидат: автофигура (НЕ текстбокс) с заливкой, ширина ≥ 100pt, высота ≥ 30pt.
- Встройка-кандидат: автофигура (НЕ текстбокс) с заливкой. У текстбоксов prstGeom=roundRect стоит по умолчанию — фигурами они не являются и в детект не входят.
- Матч: ОБА условия одновременно — left и top встройки совпадают с left и top карточки (допуск 8pt; расхождение 1–8pt — отдельный дефект выравнивания, лечится снапом), встройка уже или ниже карточки.
- НЕ дефект (исключить из детекта): обрезной декор у кромки слайда на всю его ширину/высоту, фоны размером со слайд, свободные подчёркивания заголовков и внутренние разделители карточек — они не матчатся по обеим координатам.

**Процедура исправления (для каждой пары, по порядку):**
0. Идемпотентность: если рядом уже есть маска (rect цветом карточки) и рамка (roundRect noFill габаритами карточки) — пара исправлена, ПРОПУСТИТЬ. Повторный прогон не должен дублировать конструкции.
1. Прижать: left/top встройки = left/top карточки.
2. Увеличить вглубь, запомнив видимую толщину t: шапка → ширина = ширине карточки, высота = max(2R, t + R); боковая полоса → высота = высоте карточки, ширина = max(2R, t + R).
3. Нормировать: adj = R / min(w, h) × 100000.
4. Снять собственный контур встройки (ln noFill), заливку не менять.
5. Вставить маску (z-order сразу над встройкой) и рамку-контур (над маской, ниже текстов) — параметры в паттерне выше; перекрытие маски 2pt обязательно.

**Допуск квантования EMU:** размеры хранятся в целых EMU, поэтому 12pt-габарит может записаться как 12.0019pt, а расчётный adj — как 49992–49997 вместо 50000. Расхождение радиуса в тысячные доли pt дефектом НЕ является; при аудите сверять визуальный радиус с допуском ±0,5pt, а не равенство adj.

### Карточка (Card)
```javascript
// Фон — прямые углы (вариант A)
s.addShape(pres.shapes.RECTANGLE, {

// Фон — скруглённые углы (вариант B, радиус единый по деке, §5.1)
```

### Карточки с метриками: число + единица измерения

В карточках типа «45–50 млрд руб.» или «~46,7 млрд руб.» число и единица — **единая визуальная строка**, не два независимых блока.

**Правила:**
- Число и единица стоят на одном базлайне (или с минимальным вертикальным сдвигом 3–5pt для компенсации разницы шрифтов)
- Единица идёт вплотную справа от числа
- Размер шрифта единицы — сопоставим с числом (не в 2× мельче). Допустимо: число 26pt, единица 14–16pt
- Ширина текстбокса числа должна быть достаточной, чтобы число не обрезалось («~46,7» а не «~46,»)

**Исключение — голый символ «%»**: правило «единица не мельче 2× числа» на «%» не распространяется. Знак процента может быть заметно мельче основной цифры и подан как верхний индекс (напр. число 40pt bold, «%» — 16–18pt, приподнят к верхней части цифры). Отличие от буквенных единиц («млрд руб.», «тыс. шт.») — «%» короткий и однозначно читается даже мелким и приподнятым, буквенная единица в таком виде обрежется по смыслу.

**Антипаттерн**: ставить единицу **под** числом или далеко справа с мелким шрифтом — разрывает визуальную целостность метрики. Зритель должен считать «45–50 млрд руб.» как одну цифру, а не искать глазами единицу. Для «%» это правило не про размер (см. исключение выше), а про соседство: «%» должен стоять вплотную к числу, а не оторван пробелом или переносом.


### Высота карточки — по содержимому, а не фиксированная

Высоту карточки задаёт её содержимое, а не «удобное» большое число. Карточка-контейнер фиксированной высоты, заполненная разреженным контентом (заголовок + 1–2 строки текста в плашке высотой ~4″), — дефект: контент «висит» по центру, а 60–80% плашки пустует. Это диспропорция «плашка ≫ контент» (частный случай антипаттерна §1.2 «случайная дыра»), даже если контент внутри отцентрирован правильно. Типовая причина — общий генератор/шаблон карточек с жёстким `cardHeight` на всех card-слайдах независимо от объёма текста.

**Правило:**
- Высота карточки = `2×pad + высота_заголовка + зазор + высота_текста`, в разумном коридоре (ориентир: min ≈ 2.0–2.2″, max ≈ 4.3″). Высота — переменная, а не константа шаблона.
- Все карточки одного ряда — единой высоты = max по содержимому ряда (иначе парные плашки разной высоты, §К).
- Ряд карточек **вертикально центрируется в зоне контента** (1.5–4.7″): симметричный воздух сверху и снизу, а не растягивание плашки на всю зону.
- Контент внутри карточки центрируется отдельно (см. «Распределение контента внутри карточки» ниже) — это второй уровень центрирования, не замена первому.
- Контента мало (одна короткая мысль на карточку) — не раздувать плашку: либо сжать её под контент, либо укрупнить кегль (заголовок ≥ 16pt, текст ≥ 13–14pt).

**Проверка (доля заполнения):** содержимое должно занимать ≥ ~40% высоты карточки. Если контент занимает < 40% — карточка переразмерена: уменьшить высоту или укрупнить кегль.

**Антипаттерн:** карточки фиксированной высоты (напр. 4.15″) на всех card-слайдах независимо от объёма текста — на разреженном контенте превращаются в пустые боксы (диспропорция плашка/шрифт).

### Распределение контента внутри карточки

Элементы внутри карточки-контейнера (лейбл, число+единица, описание) должны быть **равномерно распределены по вертикали**.

**Метод:**
```
свободное_место = cardHeight - Σ(высот_элементов)
padding_top = padding_bottom = свободное_место / (N_зазоров + 2)
```

**Важно:**
- Если текст двухстрочный, его высота ≥ 32–36pt, иначе текст вылезет за фигуру
- Всегда проверять: `element.bottom ≤ container.bottom - padding`
- Отступы сверху и снизу — примерно равные

**Антипаттерн**: элементы прижаты к верху карточки, нижняя треть пустует. Или наоборот — описание вылезает за нижний край контейнера.

### Внутренняя вёрстка карточки: номер + заголовок + текст (равные поля)

Карточка с тремя элементами (крупный номер сбоку, заголовок-метка, пояснительный текст) компонуется по правилу РАВНЫХ ПОЛЕЙ, а не «по умолчанию сверху вниз». Это строгий частный случай «Распределения контента внутри карточки» (выше) для карточки «номер + заголовок + текст».

**Правило:**
- Блок «заголовок + пояснение» центрируется по высоте карточки: верхнее поле (от верхней кромки карточки до верха заголовка) ≈ нижнее поле (от низа текста до нижней кромки). Допуск ±2pt. Текст НЕ должен быть прижат к нижней кромке.
- Заголовок выровнен по ВЕРХНЕЙ границе номера (top заголовка = top номера, ±1pt), а не по центру номера. Номер крупнее (≈18pt), заголовок ≈14pt — выравнивание по верху создаёт единую базовую линию.
- Пояснительный текст идёт сразу под заголовком с зазором 2–4pt (не «отрывается» к низу карточки).
- У ВСЕХ текстблоков карточки единый вертикальный якорь `anchor="t"` и обнулённые верх/низ-инсеты (`tIns=0, bIns=0`). Иначе совпадение top-координат боксов не даёт совпадения позиции глифа — текст «плавает».

**Ролевые размеры (фиксированные по всей деке):**
- Номер карточки: 18pt, bold, accent.
- Заголовок-метка: 14pt, bold, CAPS (`cap="all"`). Один размер на ВСЕХ карточках — разнобой 12,5 / 14pt недопустим.
- Пояснение: 10,5–12pt, regular, роль `palette.text.muted` активного профиля.

> Кегли 18 / 14 / 10,5–12 — дефолты. Если задан брендбук со своей шкалой — привязывать к ней, сохраняя пропорцию «номер > заголовок > пояснение» и единый кегль заголовков-меток по всей деке.

**Критерий проверки (механически):** для каждой карточки `top_gap = top(заголовок) − top(карточка)`; `bottom_gap = bottom(карточка) − bottom(текста)`; карточка гармонична ⟺ `|top_gap − bottom_gap| ≤ 2pt` И размер всех заголовков-меток в деке одинаков.

**Антипаттерн:** текст прижат к низу плашки при пустом поле сверху; заголовки разных карточек разного кегля; заголовок центрирован по номеру вместо выравнивания по верху.

### Ширина блока карточек — золотое сечение

Ключевой принцип: блок текстовых плашек НЕ должен идти одной длинной строкой через весь лист — взгляд «едет», текст теряет читаемость. Отсюда ДВА допустимых решения; промежуток между ними — дефект.

**Решение A (базовое) — золотое сечение, узкий блок + правый элемент:**
- Блок плашек ≈2/3 ширины контентной зоны (0.618; практ. 0,6–0,66), правая ≈1/3 — под ОДИН смысловой элемент: вертикальная карточка-вывод, крупная сводная цифра/метрика, мини-диаграмма или схема-воронка.
- Зазор между блоком плашек и правым элементом ≈20pt (≥0.3").
- **Расчёт (только для A):** при контентной зоне ширины W — плашки ≈0,62×W, правый элемент ≈0,33×W, зазор ≈0,05×W (но ≥20pt).

**Решение B (допустимое исключение) — полная ширина:** плашки занимают всю ширину ТОЛЬКО когда справа осознанно нет смыслового элемента И это не порождает длинную строку текста через весь лист (короткий контент в карточках, или ряд карточек, заполняющий ширину; табличный/диаграммный блок). Тогда расчёт A не применяется.

**Дефект — промежуток между A и B:** суженные плашки (ratio ≈0,7–0,9) с ПУСТОЙ правой третью; либо текстовые плашки во всю ширину одной edge-to-edge строкой. Сама по себе полная ширина НЕ дефект — дефектны только пустое правое поле при неполной ширине и длинная строка при полной.

**Критерий проверки.** Гармонично ⟺ выполнено ОДНО из: **(A)** ratio = ширина блока / контентная зона ∈ [0.58, 0.66] И правая треть занята смысловым элементом; **(B)** ratio ≳ 0,95 И нет длинной edge-to-edge строки текста. Любое промежуточное (ratio ≈0,7–0,9) с пустым правым полем — дефект.

### Callout (выноска с боковой полоской)
```javascript
s.addShape(pres.shapes.RECTANGLE, { x, y, w, h, fill: { color: C.light } });
s.addShape(pres.shapes.RECTANGLE, { x, y, w: 0.06, h, fill: { color: accentColor } });
// Текст с отступом от левого края на 0.2"
```


**Центрирование текста в callout (ОБЯЗАТЕЛЬНО):**

Паттерн callout-бара: Rectangle (фон) + узкий Rectangle (акцентная полоска) + TextBox (текст). TextBox должен:
- Совпадать с Rectangle по `top` и `height` (или быть чуть меньше с равными отступами)
- Иметь `anchor="ctr"` (вертикальное выравнивание по центру)

**Важно**: просто совместить top/height **недостаточно** — текст внутри TextBox по умолчанию прижат к верху (`anchor="t"`). В OOXML нужно выставить `<a:bodyPr anchor="ctr"/>`. В python-pptx: `tf.paragraphs[0].alignment` + `txBox.text_frame.word_wrap = True` + вручную через XML. В pptxgenjs: `valign: "middle"`. Без этого текст визуально не по центру даже при идеальном совпадении фигур.


### Акцентная линия
```javascript
s.addShape(pres.shapes.RECTANGLE, {
  x: 0.7, y: 0.85, w: 0.8, h: 0.04, fill: { color: C.accent },
});
```


### Размещение callout-бара (метод расчёта)

Callout-бар — **нижний элемент зоны контента** (§1.0). Его позиция определяется от нижней границы контента, источник при этом остаётся в футер-строке (y=4.85) и с callout не конкурирует:

```
calloutHeight = 0.3"  (1 строка) или 0.4"  (2 строки)
calloutTop = 4.7" - calloutHeight      // 4.7" = нижняя граница зоны контента (§1.0)
```

Если callout не помещается (контент опускается ниже `calloutTop`):
1. Уменьшить зазоры между верхними блоками (НЕ сжимать callout)
2. Если всё равно не влезает → вынести вывод в action title
3. Никогда не опускать callout в зону футера (y + h > 4.7")


## 6. Диаграммы

### Общие правила
- **Шрифт в диаграммах = активная гарнитура деки** (§2, стандартно Aptos; в диаграммах — текстовый Aptos, не Display). Всегда задавай `catAxisLabelFontFace`, `valAxisLabelFontFace` если pptxgenjs поддерживает, иначе — шрифт наследуется
- **Минимальный fontSize**: 10 pt для всех подписей (оси, data labels, легенда)
- **Цвета**: из палитры презентации. Для одной серии — один цвет (accent). Для нескольких — массив из палитры
- **Сетка**: только горизонтальная (valGridLine), вертикальную скрыть (`catGridLine: { style: "none" }`)
- **Легенда**: показывать только при 2+ сериях. Позиция: `"b"` (внизу)
- **Data labels**: `showValue: true`, позиция `"outEnd"` для столбчатых

### Факт vs прогноз (ОБЯЗАТЕЛЬНО)
Если диаграмма содержит и фактические, и прогнозные данные — визуально разделять. Приёмы: разный оттенок столбцов (прогнозные — светлее на 30%), пометка «п» или «прогноз» в подписях оси X, или разделительная вертикальная линия между последним фактом и первым прогнозом. Зритель ВСЕГДА должен понимать, где заканчивается реальность и начинается экстраполяция.

### Серый для не-геройских рядов (ОБЯЗАТЕЛЬНО при 2+ категориальных сериях/столбцах)

Отдельная ось от «факт vs прогноз» выше (та разделяет реальность и экстраполяцию; эта — расставляет смысловой приоритет внутри категорий). Если диаграмма показывает несколько категориальных рядов или столбцов одного среза (каналы, сегменты, конкуренты, периоды) — акцентный цвет деки получает только смысловой герой (то значение, вокруг которого построен вывод слайда), остальные ряды гасятся в нейтральный серый (`palette.lines.row` / `muted`, не второй акцентный цвет). Data labels следуют той же логике: у героя — крупный жирный акцентным цветом, у остальных — мельче, серым.

- **Не путать** с «максимум 2 акцентных цвета» (§3) — здесь один акцент на всю диаграмму, а не два разных.
- **Не путать** с семантическими цветами (§3) — если ряды несут самостоятельную семантику (каждый суббренд/конкурент — свой цвет), это исключение сохраняется; серым гасятся именно неразличаемые по смыслу «остальные», а не поимённо закреплённые сущности.
- Обе оси (факт/прогноз и герой/остальные) могут применяться одновременно на одной диаграмме: прогнозный столбец героя — акцент светлее на 30%; прогнозные столбцы прочих категорий — серый светлее.

Источник: курс Bonnie&Slide, чек-лист «100% убойный график» п.5 «Не забыть про серый» + живой пример редизайна («Digital» синим, «ТВ»/«Прочее» серым) — `tokens/_pptx-course-extracts/slajdy-u3-grafiki-tablicy.md`.

### Точность data labels
Data labels должны отражать точность исходных данных. Если значения в отчёте — с десятыми (13,2 млрд), на диаграмме тоже должно быть 13,2, а не 13. Округление до целых допустимо только если все значения > 100 или если десятые не несут смысловой нагрузки.

### Конечные data labels для линейных диаграмм
На линейных диаграммах с прогнозом ОБЯЗАТЕЛЬНО показывать data labels хотя бы на конечных точках каждой серии (значения к целевому году). Это ключевые цифры, ради которых строится прогноз.

### Цветовое кодирование шкал
Для диаграмм типа «рейтинг/статус по категориям» (импортозамещение, зрелость, готовность) использовать цветовую шкалу: красный (< 30%), жёлтый/оранжевый (30–70%), зелёный (> 70%). Превращает справочную диаграмму в стратегическую.

### Экстремальные выбросы в данных
Если один показатель в 10+ раз больше остальных, НЕ ставь его на одну диаграмму — масштаб убьёт остальные значения. Решение: вынеси выброс в отдельный callout-блок рядом с диаграммой.

### 6.1 Алгоритм выбора типа диаграммы

**Динамика (изменение во времени):**
- < 6 периодов → столбчатая (column)
- 6–12 периодов → столбчатая или линейная
- > 12 периодов → только линейная (line)
- Горизонтальная bar chart для временных рядов — ЗАПРЕЩЕНА (timeline строго по оси X)

**Структура / доли целого (сумма = 100%):**
- 2–5 элементов → pie или doughnut
- 6–10 элементов → treemap или bar chart
- > 10 элементов → bar chart
- Подписи не влезают в секторы круга → treemap

**Сравнение / рейтинг категорий:**
- ≤ 10 категорий + короткие подписи → column chart
- > 10 категорий ИЛИ длинные подписи → bar chart (горизонтальная)

**Количество подписей и пространство:**
- Если подписи категорий не влезают горизонтально под столбцами — переключись на bar chart
- Подписи под углом — антипаттерн: значит, колонок слишком много или подписи слишком длинные
- Если пространство меньше половины ширины слайда — bar chart предпочтительнее column

**Pie chart — правила:**
- Подписи — внутри секторов, НЕ в легенде. Легенда у pie chart — антипаттерн: заставляет бегать глазами между секторами и легендой
- Первый сектор начинается в позиции «12 часов», сортировка от большего к меньшему
- Мелкие секторы — подписи снаружи, не больше 2–3 таких

### 6.2 Восемь грубых ошибок диаграмм

1. **Неверный тип графика** — данные тяжело сравнивать (pie для динамики, bar для timeline)
2. **Плохо подобраны цвета** — позитивные ответы красным, негативные зелёным; цвета не несут семантики
3. **Лишние элементы** — легенда дублирует data labels; сетка + data labels одновременно
4. **Не указана единица измерения** — непонятно: штуки, проценты, тысячи, миллиарды?
5. **Неудобный формат чисел** — лишние знаки после запятой; большие числа без разделителей разрядов
6. **Слишком много секторов в pie** — более 5–6 секторов → данные невозможно сравнить визуально
7. **Сумма секторов ≠ 100%** — грубейшая ошибка; круг — это ВСЕГДА 100%
8. **Навороченный дизайн** — 3D, градиенты, тени, декоративные рамки отвлекают от данных и искажают восприятие. **3D-диаграммы ЗАПРЕЩЕНЫ** — ближний сектор кажется крупнее дальнего

### 6.3 Waffle / dot-matrix и пирамида-иерархия

Два типа визуализации сверх базовых. Цвета — из активной палитры деки (§3 / §15), без градиентов; геометрия углов плашек — по дизайн-системе деки (§5.1).

**Waffle / dot-matrix** — «X из 100» наглядно.
- **Когда**: доля, охват, прогресс, готовность как часть от целого (доля рынка, % выполнения).
- **Механика**: сетка 10×10 = 100 ячеек; закрашена доля акцентным цветом, остальное — нейтральный (§3). Ячейки прямоугольные, равные зазоры.
- **Когда НЕ применять**: сравнение многих категорий → bar; динамика во времени → line; точные доли с десятыми → waffle округляет до целых процентов.

**Пирамида-иерархия** — уровни с вложенностью или приоритетом.
- **Когда**: иерархия (стратегия → тактика), уровни потребностей, воронка ценности.
- **Механика**: 3–5 горизонтальных уровней, ширина уровня = объём/важность; подпись внутри или сбоку; один акцент — на вершину или основание.
- **Когда НЕ применять**: уровни равнозначны → нумерованный список/карточки; это поток/процесс → таймлайн или стрелки; > 5 уровней — не читается.

### Сниппеты (pptxgenjs)

**Waffle 10×10.** `pct` — доля в процентах (0..100), заполнение снизу вверх:
```javascript
function addWaffle(s, pres, { x, y, cell = 0.28, gap = 0.06, pct, on = C.accent, off = C.border }) {
  const filled = Math.round(pct);                 // до целых %
  for (let i = 0; i < 100; i++) {
    const row = Math.floor(i / 10), col = i % 10;
    const rank = (9 - row) * 10 + col;            // снизу вверх, слева направо
    s.addShape(pres.shapes.RECTANGLE, {
      x: x + col * (cell + gap),
      y: y + row * (cell + gap),
      w: cell, h: cell,
      fill: { color: rank < filled ? on : off },
    });
  }
}
// cell 0.28 + gap 0.06 → блок ≈ 3.34" × 3.34"
```

**Пирамида из уровней** (сверху узкий → снизу широкий, акцент на вершину):
```javascript
function addPyramid(s, pres, { cx, topY, levelH = 0.7, gap = 0.05, levels, maxW = 5.0 }) {
  // levels сверху вниз: [{ label, wPct }], wPct 0..1
  levels.forEach((lv, i) => {
    const w = maxW * lv.wPct, y = topY + i * (levelH + gap);
    s.addShape(pres.shapes.RECTANGLE, {
      x: cx - w / 2, y, w, h: levelH,
      fill: { color: i === 0 ? C.accent : C.light },
      line: { color: C.border, width: 0.5 },
    });
    s.addText(lv.label, {
      x: cx - w / 2, y, w, h: levelH, align: "center", valign: "middle",
      fontFace: "Aptos", fontSize: 12, color: i === 0 ? "FFFFFF" : C.body,
    });
  });
}
// 4 уровня wPct [0.4, 0.6, 0.8, 1.0] — классическая пропорция
```
Уровни — центрированные прямоугольники возрастающей ширины (stepped-пирамида): печатается чисто и предсказуемо. Истинно треугольная пирамида потребует TRAPEZOID на каждый уровень с подгонкой — для строгой деки stepped-вариант предпочтительнее.

### 6.4 Приёмы оформления и данные
- **Иконки вместо текстовой легенды.** Где возможно — заменять подписи легенды графическими иконками рядом с данными, либо подписывать прямо у точек/секторов. Снижает «бег глазами» между легендой и графиком. Для pie/doughnut — подписи в секторах (§6.1), не легенда.
- **Связь Excel → PowerPoint.** Для регулярно обновляемых цифр (финмодель, помесячный факт) — вставлять диаграмму/таблицу связанным объектом (Вставка → Объект → Создать из файла → Связать): при изменении исходного .xlsx данные на слайде обновляются. Минус: связь рвётся при переносе файла без исходника — для отправки наружу делать копию с внедрёнными данными, а не связанными.

## 7. Таблицы

### Стиль
- **Заголовок**: тёмный фон (dark), белый текст, bold
- **Ячейки**: fontSize ≥ 10pt, цвет body, valign: "middle"
- **Границы**: тонкие, светлые, дефолт **1pt** (0,5pt неразличима с проектора) — `{ pt: 1, color: C.border }`. Для показа с проектора допустимо утолщать до 2,25pt (верхний предел, не размывать линию сильнее).
- **Highlight строки бренда**: заливка — светлый тинт роли `palette.accent.primary` активного профиля (~10% непрозрачности/осветления, считать от accent, не хардкодить отдельный HEX), текст — сама роль `palette.accent.primary`, bold

### Ширина столбцов
Задавай явно через `colW: [...]` — автоматический расчёт часто даёт плохой результат. **ОБЯЗАТЕЛЬНО**: проверяй, что заголовки шапки не переносятся на вторую строку из-за узкого столбца. Если слово не влезает — сокращай текст заголовка (например, «Динамика» → «Рост», «Профессиональный» → «Проф.»), а не терпи перенос. Перенос в шапке таблицы (типа «Динамик\nа») — грубый дефект.

### Рейтинг-индикатор (качественная шкала вместо слов)
Столбец с качественным вердиктом («эффективно» / «средне» / «слабо», «высокий» / «средний» / «низкий» и т.п.) — заменять словесный текст на 1–3 закрашенных квадратика: 3 закрашенных = высшая оценка («эффективно»), 2 = средняя, 1 = слабая (не путать с data labels, §6 — здесь визуальная шкала заменяет весь текст ячейки, а не дополняет число).
- Квадраты — маленькие (≈0.1"), в один горизонтальный ряд по 3 на ячейку, равный зазор.
- Закрашенные — акцентным цветом (`C.accent`); незакрашенные — `C.border`/`muted` (не пустые/невидимые — контур или заливка нейтральным, чтобы 1 из 3 не читался как «пусто»).
- Один и тот же цвет закраски для всех строк — вердикт кодируется КОЛИЧЕСТВОМ закрашенных, не цветом (цвет как дополнительная семантика — на усмотрение, но не обязателен).
- Дублировать текстовым тултипом/сноской не нужно — квадраты читаются мгновенно; если аудитория незнакома с форматом, один раз пояснить в подписи «●●● эффективно / ●● средне / ● слабо».

Источник: курс Bonnie&Slide, редизайн таблицы урок 3 — колонка «Вывод» заменена тремя синими квадратами (`tokens/_pptx-course-extracts/slajdy-u3-grafiki-tablicy.md`).

### Пустое пространство под таблицей
Если таблица занимает менее 2/3 высоты слайда — добавить callout-вывод в свободную зону. Пустая нижняя треть слайда — не «воздух», а неиспользованное пространство.

### Высота строк
Задавай через `rowH: [...]`. Заголовок обычно чуть выше: 0.35–0.4", данные: 0.3–0.38".

## 8. Титульный слайд

- Тёмный фон (dark)
- Акцентная линия сверху
- Название — крупно (36–42pt), белый, bold, charSpacing: 4
- Подзаголовок (бренд/объект) — тем же размером, accent color
- Описание — не менее 14pt, muted. Это единственная строка, объясняющая зачем открывать файл — она должна быть заметной
- Автор/дата — внизу, мелко (11pt), muted
- **Не штамповать «передано / дата передачи / сдано ДД.ММ.ГГГГ» на титуле** — это язык сопроводительного письма (transmittal), а не презентации; так не пишут. Если нужна привязка ко времени — дискретная версия/дата внизу мелким muted (напр. «2026» или «v1.2»), не как штамп о передаче в подзаголовке
- **Логотип заказчика**: если презентация подготовлена для конкретной компании — логотип обязателен (правый нижний угол или рядом с автором). Повышает доверие
- **Вертикальный баланс**: заголовок должен доминировать визуально, располагаясь в верхней трети слайда (y ≈ 1.2–1.6), а не «проваливаться» в центр. Пустая верхняя половина — это не воздух, а пустота

### Вариант: фото-фон со скримом (осознанная замена сплошного тёмного фона)

Дефолт титула — сплошной тёмный фон (`C.dark`). Допустимая альтернатива — фото-фон, формула:
1. Релевантное качественное фото (по теме презентации, не абстрактный сток) на весь слайд.
2. Кроп «Пропорции 16:9» (или программный crop под 10"×5.625") — фото заполняет слайд без искажения пропорций (§16, Fill).
3. Фото — на задний план (`sendToBack` / нижний z-order).
4. Поверх — чёрный скрим: прямоугольник на весь слайд, заливка `000000`, прозрачность **65%** (приглушает, не обесцвечивает фото).
5. Текст (заголовок, подзаголовок, автор/дата) — белым поверх скрима, композиция как в дефолтном варианте (§8 выше).

**Оговорка (жёсткая, согласуется с §16):** только качественное релевантное фото — фото самого объекта, проекта, локации, продукта. Не сток-клише (рукопожатия, абстрактные графики, стоковые «бизнесмены»). Если подходящего фото нет — использовать дефолт (сплошной тёмный фон), не тянуть случайный сток ради приёма. Дефолт остаётся сплошной тёмный фон — фото-вариант это осознанный выбор, а не замена по умолчанию.

Источник: курс Bonnie&Slide, пересборка титула («Бьём итоги по охвату», проба скрима 30% → финал 65%) — `tokens/_pptx-course-extracts/slajdy-u2-zapomnyat.md`.

## 11. Сетка карточек

Для 3 карточек в ряд:
```
xBase = 0.7 + i * 3.0    // ширина карточки ~2.7"
```

Для 2×3 карточки:
```
col = i % 3;  row = Math.floor(i / 3);
xBase = 0.7 + col * 3.05;
yBase = startY + row * 1.85;   // карточка ~1.6" высотой
```

Для 2×3 рекомендации:
```
col = i % 2;  row = Math.floor(i / 2);
xBase = 0.7 + col * 4.6;
yBase = startY + row * 1.2;    // карточка ~1.0" высотой
```


### Парные/групповые карточки — одинаковая высота (ОБЯЗАТЕЛЬНО)

Если на слайде есть 2+ карточки в одном ряду или в одной логической группе — они **должны быть одной высоты**. Разная высота (например, 108pt и 86pt) смотрится несбалансированно.

**Метод:** `cardHeight = (availableHeight - (count - 1) * gap) / count`

Исключение: карточки с **разным приоритетом** (§11 «Визуальная иерархия в карточках»). Но даже тогда — карточки одного приоритета должны быть одной высоты.

### Визуальная иерархия в карточках (ОБЯЗАТЕЛЬНО при приоритизации)
Если карточки имеют разный приоритет / вес — это ДОЛЖНО быть видно. Приёмы: карточки высшего приоритета — крупнее (больше h), акцентный цвет полоски. Карточки низшего приоритета — мельче, приглушённый цвет. Все карточки одного размера при разных приоритетах — антипаттерн. Зритель должен считать иерархию за 2 секунды, не читая текст.

### Согласованность карточек и диаграмм
Если на слайде есть диаграмма + пояснительные карточки — карточки ДОЛЖНЫ комментировать то, что показано на диаграмме. Пример антипаттерна: doughnut с 6 товарными категориями + карточки про 3 тренда, которые НЕ являются сегментами диаграммы. Зритель в замешательстве.

## 12. Русская типографика

- Неразрывные пробелы (`\u00A0`) после предлогов (в, на, по, за, из, от, до, к, с, у, о)
- Неразрывные пробелы между числом и единицей (100\u00A0000, 25\u00A0млрд)
- Тире — длинное (—), не дефис (-)
- Кавычки — «ёлочки» для русского текста
- Деньги — словами: «тыс./млн/млрд руб.». Символ ₽ **не используется** нигде (CLAUDE.md)

### 12.1 Англицизмы — избегать (ОБЯЗАТЕЛЬНО)

Дека на русском языке пишется по-русски. Бытовые и управленческие англицизмы — маркер небрежности; для совета директоров, куратора и госзаказчика они недопустимы.

**Правило трёх категорий:**

1. **Жаргон-кальки — ВСЕГДА заменять.** Англицизм, у которого есть полноценный русский эквивалент, в деке не появляется:

| Англицизм | Замена |
|---|---|
| гейт, stage-gate | шаг, контрольная точка |
| So what (в callout) | Вывод: / Что это значит: |
| драйвер | фактор, причина |
| челлендж | задача, вызов |
| инсайт | наблюдение, вывод |
| ramp-up | выход на заполняемость / на проектную мощность |
| asking (ставка) | запрашиваемая ставка |
| benchmark | ориентир, эталонное значение |
| cost-stack | структура затрат |
| stranded power / space | запертая мощность / неликвидная площадь |
| top-down | сверху вниз |
| fit-out | технологическое оснащение |
| deadline | срок |
| кейс | пример, проект |
| AI / IT в русском тексте | ИИ / ИТ |

2. **Отраслевые термины без устоявшегося русского эквивалента — допустимы**, но при первом употреблении дать русское пояснение в скобках или рядом: colocation, retail/wholesale (розничная/оптовая модель), hyperscale (гиперскейлер), PUE, FAR (плотность застройки), liquid cooling (жидкостное охлаждение), white space (машинные залы), MMR, SLA, CAPEX/OPEX, EBITDA. Если русский эквивалент не длиннее и не теряет точность — предпочесть его.

3. **Имена собственные и источники** (JLL, CBRE, Schneider Electric, Tier III, GPU) — не переводятся.

**QA-проверка**: прогнать весь текст деки поиском по списку категории 1 — ноль вхождений. Спорный термин проверять вопросом: «поймёт ли это слово член совета, не читающий отраслевые телеграм-каналы?»

### 13.1 Critic-gate — самопроверка чужой рубрикой (ОБЯЗАТЕЛЬНО перед выдачей)

QA-чеклист выше — механический контроль. После него, ДО передачи файла пользователю,
дека проходит перцептивную самооценку по рубрике скилла-критика **pptx-critic**
(Claude Code: `~/.claude/skills/pptx-critic/SKILL.md`; claude.ai: `/mnt/skills/user/pptx-critic/SKILL.md`).

Порядок:

1. **Рендер уже есть** — использовать изображения слайдов из шагов 1–2 §13 (PDF → per-slide JPG/PNG).
2. **Смена роли.** Прочитать рубрику pptx-critic и пройти деку слайд за слайдом как внешний критик:
   пять осей Д/С/Т/Г/А по 5-балльной шкале + список антипаттернов критика. Установка — найти,
   что не так, а не подтвердить, что всё хорошо; свои решения не защищать.
3. **Критерий пропуска.** Gate пройден ⟺ все пять осей ≥ 4 И среднее по осям ≥ 4.5
   И ни одного антипаттерна (§14 этого скилла + список pptx-critic).
4. **Исправление.** Блокирующее (ось < 4, среднее < 4.5, антипаттерн) чинится точечно
   (python-pptx), не пересборкой; после правок — повторный рендер и проверка исправленных мест.
   Максимум 2 итерации gate: если после второй блокирующее остаётся — файл выдаётся с явным
   списком нерешённого (не молчать о нём).
5. **Отчёт в выдаче.** Вместе с файлом — оценки осей и ПОЛНЫЙ список находок с рангами
   (формат отладочный, на период обкатки gate; после стабилизации можно ужать до короткой сводки):

   ```
   Gate: Д 4/5 · С 5/5 · Т 4/5 · Г 5/5 · А 5/5 (ср. 4.6) — пройден, 2-й круг
   [критично]  сл. 3: факт/прогноз одним цветом — исправлено (паттерн-заливка)
   [критично]  сл. 7: pie 8 секторов — исправлено (→ bar)
   [важно]     сл. 9: callout наехал на таблицу — исправлено (сдвиг y)
   [косметика] сл. 6: зазор 0.28" при норме 0.3" — осталось
   ```

**Переключатель.** Слова «черновик», «без gate», «быстрый вариант» в запросе → gate пропускается,
в выдаче пометка «черновик, без gate». Явная просьба «с рецензией» → помимо gate, полная рецензия
pptx-critic отдельным .md-файлом.

Gate ≠ рецензия: без .md-файла и без художественного послайдового разбора — только оценки
осей и ранжированный список находок. Полный формат рецензии — у pptx-critic по отдельному запросу.

- barGapWidthPct > 50% (тощие столбцы)
- «Спасибо» на последнем слайде
- **Более двух** шрифтовых семейств или несистемная смена гарнитуры внутри одного уровня
- **Имя шрифта из брендбука без сверки с файлом** — «Cera CY» в гайде vs «Cera Pro» в файлах: дека молча рендерится Calibri (§2)
- **Чинить XML, когда рендер показывает подмену шрифта** — причина в системе (нет шрифта / другое имя), порядок диагностики: система → файл шрифта → XML (§2)
- Больше 2 акцентных цветов
- Слайд с > 1 основной идеей (6×6: максимум 6 строк × 6 слов)
- Данные с 10× выбросом на одной шкале диаграммы
- Переиспользование объектов shadow/options между вызовами (pptxgenjs мутирует)
- `#` в hex-цветах (вызывает corruption)
- 8-символьные hex-цвета с opacity (используй свойство `opacity`)
- Unicode-буллеты `"•"` (создают двойные буллеты — используй `bullet: true`)
- `lineSpacing` с буллетами (используй `paraSpaceAfter`)
- **Слайд с данными без вывода «so what»** — зритель не должен сам догадываться
- **Потеря данных при переносе из отчёта** — если в отчёте 4 ценовых сегмента, на слайде должно быть 4, не 3
- **Факт и прогноз одним цветом** — зритель не отличает реальность от фантазии
- **Округление data labels с потерей смысла** — 13,2 → 13 допустимо только если десятые нерелевантны
- **Монотонная компоновка** 15+ слайдов без section dividers — зритель уходит на автопилот
- **Одинаковый размер карточек при разных приоритетах** — иерархия должна быть видна
- **Пояснительные карточки, не соответствующие диаграмме** — карточки комментируют то, что показано
- **Перенос слов в шапке таблицы** — лучше сократить текст, чем терпеть «Динамик\nа»
- **Action items без сроков на финальном слайде** — это пожелания, а не план
- **Пустая верхняя половина титульного слайда** — заголовок должен доминировать, не «проваливаться»
- **Пересборка профессиональной деки с нуля** — потеря ручной полировки, семантических цветов, данных. Точечная правка через python-pptx ВСЕГДА предпочтительнее
- **Callout «вслепую»** — размещение callout на фиксированной y-координате без проверки свободного пространства → наложение на таблицы/диаграммы
- **Action title > 60 символов** — переносится на 2 строки, ломает вертикальный бюджет
- **Унификация семантических цветов** — замена 6 уникальных цветов суббрендов на 2 акцентных → потеря визуальной идентичности
- **Размещение элементов без расчёта вертикального бюджета** — считать ДО кода, не после
- **«Гуляющий» футер** — источник/номер на разных y от слайда к слайду; сноска ниже номера слайда; двухстрочная сноска, выползающая к краю листа. Футер-строка фиксирована: y=4.85, h=0.25, одна базовая линия (§1.0, §4)
- **3D-диаграммы** — искажают восприятие данных, ближний сектор кажется крупнее. ЗАПРЕЩЕНЫ
- **Pie chart с > 6 секторами** — не читается; заменять на treemap или bar
- **Pie chart с суммой ≠ 100%** — круг всегда 100%, иначе диаграмма лжёт
- **Легенда у pie chart вместо подписей в секторах** — заставляет бегать глазами
- **Легенда, дублирующая data labels** — лишний элемент, убрать одно из двух
- **Отсутствие единицы измерения на диаграмме** — зритель не знает: это %, тыс., млрд?
- **Числа без разделителей разрядов** — 1000000 vs 1 000 000
- **Подписи категорий под углом** — сигнал, что нужна горизонтальная bar chart
- **Длинные буллит-листы вместо карточной вёрстки** — Bento-дизайн предпочтительнее стены текста
- **Смешение стилей иконок** — outline + filled + 3D в одной деке; нужен один набор (§1.2)
- **Отсутствие доминанты на слайде** — все элементы одного размера, взгляд «плавает»
- **Широкая таблица во всю ширину слайда** при наличии профильных KPI — «разъезжаются глаза», правый край пустует. Делить по золотому сечению (§15)
- **Выравнивание заголовка по тексту первой ячейки**, а не по краю карточки таблицы — край «гуляет» (§15)
- **Разнобой геометрии углов** — смешение прямых и скруглённых плашек в одной деке, либо визуально разные радиусы на плашках разного размера. Причина — одинаковый adj без нормировки под min(w, h); лечится `set_corner_radius()` (§5.1)
- **Символ ₽** вместо «руб.» словами — везде, не только в колоде «Иначе» (§12)

## 15. Паттерн «Финтаблица + KPI-плашки» (бренд «Иначе»)

Проверенный модуль для финансовых слайдов (P&L, выручка, маржинальность): **таблица слева по золотому сечению + KPI-плашки справа**. Заменяет голую широкую таблицу во всю ширину слайда.

### Фон и брендинг (на мастере, не на слайде)
- Фон страницы: `fills.paper` профиля inache (светло-серый, F4F5F7 в tokens/inache.json), без подтонов, на ВСЕХ слайдах включая титульный.
- Вертикальная teal-полоса слева (`accent.primary` профиля inache, 23B3B4, ширина ≈12pt, на всю высоту) + текст-логотип «Иначе» в левом верхнем углу. **Не путать** с `accent.signal` (00E8E8, яркая бирюза) — тот зарезервирован только для точечных сигналов (стрелки/маркеры/подчёркивания), не для полос и заливок (см. tokens/inache.json, rules.signal_scope).
- Эти элементы — на slideMaster, не дублируются по слайдам.

### Оболочка карточки (deck-стандарт «Иначе» — переопределяет §5 Card)
Любое полотно поверх серого фона (таблица, KPI-плашка, блок данных, диаграмма):
- Заливка чисто белая `FFFFFF`.
- Граница `1pt lines.card` профиля inache (D7DAE0 в tokens/inache.json), углы **скруглённые, радиус 6pt**, нормирован через adjustment для каждой фигуры (§5.1) — визуально одинаков на таблице, KPI-плашках и блоке диаграммы. Тонкие акцентные полоски остаются прямоугольными (§5.1).
- Тень: вертикальное смещение 3pt, без горизонтали, blur 14pt, `000000`, alpha 8%. OOXML: `<a:outerShdw blurRad="177800" dist="38100" dir="5400000"><a:srgbClr val="000000"><a:alpha val="8000"/></a:srgbClr></a:outerShdw>`.

### Композиция по золотому сечению (16:9, 960×540pt)
- Рабочая ширина 48…912pt (864pt). Делёж 1/φ: **таблица ≈534pt слева**, **KPI-зона ≈292pt справа**, воздух между ними ≈18pt.
- Заголовок слайда и подпись-сноска выравниваются по **левому краю КАРТОЧКИ таблицы** (она на 18pt левее первой колонки), а НЕ по тексту в ячейках. Иначе край заголовка «разъезжается» с краем таблицы.
- KPI-плашки выровнены по верхнему и нижнему краю карточки таблицы: `cardH_kpi = (cardH_table − gap)/2`. Равный зазор между ними.

### Таблица — внутренний канон (из xlsx-style, адаптирован под слайд)
- Шапка таблицы: тёмная заливка `1F3A5F`, белый bold, усиленная линия снизу `808080`.
- Столбец «Ед. изм.» — узкий, по центру. Подписи строк — влево. Числовые столбцы — вправо (выравнивание разрядов).
- Отрицательные — бордовым `9C2542`, с минусом (не скобки). Ноль — серым `A6A6A6`.
- Итоговая строка — bold, усиленная верхняя линия + **янтарный акцент** `C77B30` (левая граница 3pt либо значение итога янтарём). Одна тёплая точка — не плодить.
- Служебная строка (рентабельность, коэффициенты) — курсив, серый `808080`.
- Границы — только горизонтали `D9D9D9`, без вертикалей.
- Минимум шрифта в таблице на слайде — **14pt** (не 10–11pt как в §7; проекция читается из зала).

### KPI-плашка
- Лейбл (14pt, `808080`) → крупное число (36pt bold, `1F3A5F`) + единица вплотную справа (16pt, по §5 «число+единица — одна строка») → дельта (15pt bold, зелёный `2E8B57` рост / бордовый `9C2542` падение) с маркером ▲/▼.
- Числа в плашках **обязаны выводиться из таблицы** (сходимость): дельта EBITDA = (тек.−пред.)/пред.; рентабельность = EBITDA/Выручка. Подпись-сноска фиксирует формулу сверки и периметр.

### Денежные единицы
- Словами: «тыс. руб.», «млн руб.», «млрд руб.». **Символ ₽ не использовать** (общее правило, §12 / CLAUDE.md).

## 16. Изображения и иллюстрации

Строгая дека — не всегда чисто карточно-табличная. В девелоперских презентациях нужны фрагменты карт, архитектурные рендеры, фото текущего статуса объекта, продуктовые изображения. Изображение — рабочий инструмент, но по строгим правилам.

### Назначение
- Изображение **несёт информацию** (где объект, как выглядит, какой статус стройки), а не «оживляет» слайд. Декоративный сток без смысла — не вставлять.
- Один смысловой образ на слайд доминирует; не собирать коллаж из разнородных картинок.

### Качество и пропорции
- Высокое разрешение, без размытия и пикселизации. Растр **не увеличивать сверх 100%** исходного размера.
- **Никогда не искажать пропорции** (lock aspect ratio). Подгонять кадрированием (crop), а не сплющиванием.
- **Fill vs Fit**: режим Fill — изображение заполняет рамку целиком с обрезкой лишнего (фоновые и карточные фото); Fit — вписывается целиком с полями (когда нужен объект целиком, например рендер фасада). Растягивание под рамку с искажением — запрещено.

### Единый визуальный язык
- Все изображения на слайде / в разделе — в одной обработке: одинаковый тон, одинаковая рамка или её отсутствие, **углы — по геометрии карточек деки** (§5.1): в деке с прямыми углами фото прямые; в деке со скруглёнными карточками фото внутри карточек кадрируются тем же радиусом; full-bleed-изображения — всегда без скруглений.
- Сетка из нескольких фото — одинаковый размер, выровнены по сетке, равные зазоры (как карточки, §11).

### Размещение
- Два сценария: **full-bleed** (фото под обрез на весь слайд или половину) или **в карточке** с белым полем. «Висящая» картинка с тенью посреди белого фона — антипаттерн.
- **Текст поверх фото** — только с затемняющей полупрозрачной подложкой или плашкой. Без подложки текст на фото нечитаем.
- **Удаление фона**: если объект должен «врасти» в слайд, а не висеть прямоугольником — вырезать фон (PNG с прозрачностью). Особенно для продуктовых изображений и силуэтов поверх цветного фона.
- **Расширение за край (breaking the frame)**: намеренно вывести фото или форму за обрез слайда — приём для динамики и ощущения пространства. Применять к изображениям и фоновым формам, не к тексту и данным (текст держит поля ≥ 0.5", §1).

### Приёмы обработки (по необходимости)
- **Ч/б фото + цветной акцент**: обесцветить фотографию-фон и положить поверх цветной текст/иконки/данные — современный приём, даёт контраст без перегруза цветом. Обесцвечивать все фото слайда единообразно.
- **Ghost-текст / ghost-форма**: крупный полупрозрачный текст или форма на фоне (прозрачность ~8–15%) — создаёт глубину. Только если **не мешает чтению** основного контента; уместен на обложке, разделителе, концептуальном слайде — не на data-слайде. Тонкий приём, не декор ради декора (ср. §14).
- **Boolean-обрезка фото по контуру плашки/карточки**: когда декоративное фото должно лежать поверх скруглённой/фигурной карточки с чистым краем (без прямоугольного «хвоста», торчащего за пределы плашки) — сделать рабочую копию фигуры-маски того же контура, что и карточка; выбрать фото + копию-маску → «Объединить фигуры → Пересечение» (PowerPoint) либо булева операция пересечения в python-pptx/скрипте генерации. Итог — фото обрезано ровно по форме карточки, без ручного crop «на глаз». Применять только к декоративным/иллюстративным фото внутри плашек, не к data-визуалам.
- **Перекраска готовых PNG-иконок в белый без вектора**: если иконка — растровый PNG (не SVG/векторная фигура) и её нельзя перекрасить штатно — «Формат рисунка → Настройка рисунка → Яркость» выкрутить на **+100%**: иконка становится белой. Годится для приведения разномастных иконок из внешнего набора к единому белому цвету на цветной подложке (§1.2, «Единый стиль иконок»). Приём для режима точечной правки существующей деки — при сборке с нуля предпочтителен исходно белый/векторный вариант иконки.

### Подписи
- Карта, рендер, фото статуса — короткая подпись (что / где / когда), 10pt, muted.
- **Фото статуса стройки — дата съёмки обязательна.** Без даты фото статуса бессмысленно.

### Карты и схемы локации
- Показывать привязку и масштаб (где объект относительно города / трассы), убрать лишние слои, выделить объект **акцентным маркером**.

### Источники
- Приоритет — **реальные материалы проекта** (рендеры, съёмка объекта, карты). Сток (Unsplash, Pexels) — только если своего нет и изображение действительно необходимо; избегать заезженных стоковых клише.

### Чувствительный контур
- Рендеры, фото объекта, внутренние карты — внутренний материал. Наружу без необходимости не выносить (см. CLAUDE.md, п. 4).

## 17. Как строить палитру

§3 даёт готовую палитру. Этот раздел — как собрать палитру **с нуля** под новый проект, отрасль или брендбук.

### Правило 60–30–10
Пропорция площадей, а не только «максимум 2 акцента»:
- **60%** — основной/фоновый цвет (обычно белый или светлый нейтральный).
- **30%** — вторичный цвет (тёмный для текста и шапок).
- **10%** — акцент (CTA, выделение, доминанта).

Роли можно менять между слайдами для динамики, но пропорция сохраняется. Перебор акцента (10% → 40%) убивает фокус.

### Психология цвета по отраслям
Цвет несёт смысл — подбирать под содержание, а не по вкусу:

| Цвет | Ассоциации | Где уместен |
|---|---|---|
| Синий | доверие, стабильность | финансы, IT, деловые |
| Зелёный | рост, надёжность | банки, девелопмент, экология |
| Красный | энергия, срочность | CTA, акценты, триггеры |
| Графит/чёрный | статус, премиум | имидж, обложки |
| Оранжевый/янтарь | доступность, тепло | акцент, «одна тёплая точка» |
| Фиолетовый | уникальность | бренд, технологии |

Для девелопмента/банка база — **синий или тёмно-зелёный + графит**, акцент — красный или янтарь.

### Цвета фона по теме
- Бизнес/финансы → графит, тёмно-зелёный, тёмно-синий, золото/янтарь как акцент.
- Светлый деловой → белый/светло-серый фон (дефолт строгой деки), тёмный — только обложка/финал/разделители.

### Схемы построения палитры (круг Иттена)
- **Монохромная** — один цвет + его оттенки → спокойствие, целостность. Лучшая для аналитических/финансовых дек.
- **Аналоговая** — соседние цвета → мягкость, гармония. Для корпоративных.
- **Комплементарная** — противоположные → максимальный контраст. Один доминирует, второй — только акцент.
- **Триада** — три равноудалённых → динамика. Для маркетинга; в строгой деке осторожно, легко перегрузить.

Для строгой деловой деки безопасны **монохромная** и **аналоговая** + один комплементарный акцент.

### Рабочие схемы (референс)
Частые проверенные сочетания:
- Тёмный фон (графит/тёмно-синий) + один яркий акцент → tech, финансы, IT.
- Белый/светло-серый + один яркий (синий, красный, оранжевый) → универсальный бизнес.
- Жёлтый + чёрный → энергичная инфографика (применять осторожно, агрессивно).
- Зелёный + белый → девелопмент, эко, здоровье.
- Синий + белый → классика, финансы, госсектор.

### Чего избегать
- Фиолетовый + оранжевый и подобные кричащие дисгармоничные пары.
- «Радужность» — несколько полноцветных без доминирующего (нарушает 60–30–10).
- Градиентные фоны с 3+ переходами; в строгой деке — плоские заливки.

### Связь с §3
Собранная по этим правилам палитра записывается в объект `const C = {...}` (§3) и дальше работает как фиксированная. Семантические цвета (§3) — поверх базовой палитры, по числу сущностей.

## 18. Каталог макетов слайдов

Скилл выше говорит, *как оформить* слайд. Этот раздел — *что выбрать* под мысль. Все макеты бренд-агностичны: цвета берутся из активной палитры (§3 / §15), без привязки к конкретным hex, без градиентов; геометрия углов — из дизайн-системы деки (§5.1).

### 18.0 Паспорт слайда (4 оси)
Перед вёрсткой каждого слайда осознанно определить его по четырём осям — страховка от случайной вёрстки:
1. **Тип контента** — график / таблица / карта / фото / иконки / инфографика / схема.
2. **Структура** — сравнение / цифра-герой / буллиты-карточки / таймлайн / цитата / диаграмма / процесс.
3. **Стиль** — минимализм / акцентный / тёмный / светлый (в рамках дизайн-системы, §0 пре-флайт).
4. **Контекст** — аудитория и отрасль (§19 адаптация, §17 психология цвета).

### 18.1 Матрица «задача → макет → механика»

| Коммуникативная задача | Макет | Ключевая механика |
|---|---|---|
| Открыть раздел, дать передышку | Section divider | Тёмный/акцентный фон, номер раздела 48–56pt, название; без шапки и источника (§4) |
| Усилить тезис голосом эксперта/клиента | Цитатный слайд | Цитата ≤ 2 строк (24–32pt), атрибуция мельче, акцентная кавычка/линия; минимум фона |
| Перечислить шаги/факторы по порядку | Нумерованный список 01–0N | Крупные номера слева как навигация + доминанта; заголовок + пояснение, не буллиты (§1.2) |
| Показать этапы/вехи во времени | Таймлайн | Горизонтальная ось времени, ≤ 5–6 вех с датами и подписями; факт и план различать (§6, «факт vs прогноз») |
| Подать одну ключевую цифру | KPI-баннер («цифра-герой») | Одна гигантская цифра (54–96pt, ≥ ⅓ площади слайда) + единица + короткий контекст; один фокус на слайд |
| Разложить идею на 4 аспекта | 2×2 нумерованные карточки | Четыре равных блока (номер + заголовок + пояснение), одинаковая высота (§11) |
| Дать три равнозначных аргумента | Триптих | Ровно 3 вертикальных блока (иконка + заголовок + 1–2 строки); 4 пункта → сетка 2×2 |
| Совместить аргументы и визуал | Split-layout 50/50 (60/40) | Текст/данные/иконки слева, фото/иллюстрация справа под обрез; жёсткая граница зон (§16) |
| Показать трансформацию / сравнение | До/после | Два блока: «было» (приглушённо) и «стало» (акцент), или стрелка между; контраст состояний |
| Объяснить механизм / workflow | Схема-процесс | Блоки одного размера, связанные стрелками одного веса (линейно или цикл); 1 блок = 1 шаг |
| Показать набор метрик разом | Сетка KPI | 3–6 плашек «число + единица + дельта» (§5 / §15), выровнены по сетке |
| Показать динамику/сравнение | Полноширинный график | Один график на слайд (§6) + callout «so what» (§4) |
| Привязать данные к географии | Карта с пинами | Карта-подложка, объекты — акцентными маркерами, масштаб/привязка (§16) |
| Показать объект/статус визуально | Фото-карточки 01/02/03 | 2–3 фото одного размера, выровнены, подпись с датой (§16) |
| Показать доли + комментарий | Doughnut с выносками | Кольцо + выноски к секторам вместо легенды, ≤ 6 секторов (§6.1) |
| Показать иерархию/приоритет | Пирамида | 3–5 уровней, ширина = объём/важность (§6.3) |
| Показать долю/охват наглядно | Waffle / dot-matrix | Сетка 10×10, закрашена доля (§6.3) |
| Закрыть деку результатом | Финал-достижение | Ключевой итог/CTA крупно, без «Спасибо», тёмный фон-рамка (§9) |

**Диверсификация**: не повторять один макет 3+ слайда подряд — чередовать для ритма. Монотонность макетов усыпляет так же, как монотонность 15+ слайдов без разделителей (§4).

### 18.2 Принципы передачи мысли

Извлечены из устройства профессиональных образцов — работают на любой палитре:

1. **Один макет = одно сообщение.** Если на макете больше одной мысли — это два слайда (§1).
2. **Крупный номер как навигация + доминанта.** 01–0N задаёт порядок чтения и сразу создаёт доминанту (§1.2).
3. **Инлайн-подсветка ключевых слов.** Выделять акцентным цветом 1–3 ключевых слова в тезисе, а не весь текст (§3). Подсветка всего = подсветка ничего.
4. **Ритм через чередование заливки.** Чередование фона блоков/секций создаёт визуальный ритм — это структурный приём, не украшение.
5. **Метрика «число + единица + дельта» одной строкой.** Число крупно, единица вплотную справа, дельта с маркером ▲/▼ (§5 / §15).

## 19. Нарратив деки

§4 — структура одного слайда. Этот раздел — рассказ всей деки: порядок, логика, эмоция.

**Если в материалах есть `presentation-blueprint.md` (выход скилла pres-blueprint)** — маршрут,
аудитория, целевая эмоция, тезис и план экранов берутся из него, а не выводятся заново; этот
раздел используется для проверки (тест storyline ниже), а не для повторной смысловой работы.
Утверждения со статусом «нужно проверить» из блока 5 blueprint не выносятся на слайды как
факты до верификации (fact-checker-pro).

### Универсальная структура (5 блоков)
1. **Контекст / завязка** — где мы и почему это важно сейчас. Захват внимания.
2. **Проблема / напряжение** — что не так, риск, разрыв. Без проблемы решение не нужно.
3. **Решение** — что предлагаем, в чём суть и преимущество.
4. **Доказательная база** — цифры, модель, кейсы, статус. Здесь живут data-слайды (§6, §7).
5. **Вывод + действие** — главный итог и конкретный следующий шаг (§9, финал с действиями и сроками).

Не каждая дека строго линейна, но эти пять ролей должны быть закрыты. Раздел без доказательной базы — декларация; без вывода — справка без адресата.

### Тест storyline (ОБЯЗАТЕЛЬНО)
Прочитать подряд **только action title'ы** всех слайдов (§4 «so what»). Если из заголовков складывается связный рассказ по логике «контекст → проблема → решение → доказательство → действие» — нарратив есть. Если получается набор тем («Рынок», «Финмодель», «Риски») — заголовки описывают, а не доносят. Переформулировать в тезисы.

### Адаптация под аудиторию
Один и тот же проект подаётся по-разному:
- **Банк / инвесткомитет** → возврат и обеспечение: DSCR/LLCR, источники погашения, обеспечение, стресс-сценарии, риски и митигация. Эмоция — уверенность в возвратности.
- **Бенефициар / собственник** → стратегия и образ результата, ключевые развилки, деньги. (Для рефлектора — образно, достижения вперёд; см. CLAUDE.md.)
- **Команда** → сопричастность, роли, вклад каждого.
- **Клиент / покупатель** → выгода и удобство, а не внутренняя кухня.

Перед сборкой деки — зафиксировать аудиторию и цель (тот же вопрос задаёт pptx-critic при разборе контекста).

### Тип презентации ↔ целевая эмоция
| Тип | Цель | Эмоция |
|---|---|---|
| Питч / привлечение финансирования | получить деньги | уверенность, вера в возвратность |
| Отчёт / мониторинг | показать результат | надёжность, прозрачность |
| Стратегия | согласовать направление | ясность, контроль |
| Презентация продукта/объекта | продать | желание, ощущение выгоды |

Эмоция определяет тон: питч — напор и доказательность; отчёт — спокойствие и точность.

### Открытая петля (эффект Зейгарника)
Приём для удержания: в начале — интригующий вопрос или неожиданный факт («Почему при готовности паркинга 5% проект остаётся в графике?»), петля держится через всю деку, в финале — ответ. Не злоупотреблять: одна открытая петля на деку, иначе превращается в манипуляцию.
