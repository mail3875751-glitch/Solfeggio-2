# Схема токен-слоя

Токен-слой — общий источник дизайн-значений (цвета, шрифты, числовые форматы)
для скиллов `pptx-strict`, `xlsx-style`, `doc-style` и их пар-критиков.
Каждый бренд-профиль — JSON-файл в `tokens/`. Скилл выбирает профиль по
контексту запроса и подставляет значения вместо хардкода.

## Структура профиля

```json
{
  "profile": "<имя>",
  "inherits": "<имя-родителя>" | null,
  "palette": { ... },
  "typography": { ... },
  "number_rules": { ... },
  "brand_marks": { ... },
  "xlsx_palette_preset_default": "<имя пресета>"
}
```

Профиль может содержать не все секции — отсутствующие наследуются от
родителя (см. «Наследование» ниже). Полный набор секций задаёт только
`neutral.json` (корень наследования).

## Семантика ролей

### palette.text
- `heading` — заголовки (H1–H3, титулы). В neutral: 1A1A1A.
- `body_screen` — основной текст на экране (xlsx, pptx). В neutral: 262626.
- `body_print` — основной текст в печатном документе (docx). В neutral: 333333.
- `muted` — подписи, сноски, источники, малозначимый текст. В neutral: 808080.
- `inverse` — текст на тёмном/цветном фоне (напр. белый на шапке таблицы). В neutral: FFFFFF.

### palette.lines
- `row` — тонкая горизонтальная линия между строками таблицы. В neutral: D9D9D9.
- `strong` — усиленная линия (под шапкой, над итогом). В neutral: 808080.
- `card` — граница карточки/полотна поверх небелого фона страницы (1pt,
  скруглённые карточки на сером/цветном фоне). В neutral: `null` (нейтральный
  профиль кладёт карточки на белый фон без обособляющей границы). Первый
  профиль, кодифицирующий её — `inache` (D7DAE0, конструктивная сигнатура §15
  pptx-strict).

### palette.accent
- `primary` — основной акцентный цвет бренда (шапки таблиц, ключевые элементы).
- `secondary` — вторичный акцент (заголовки выносок, вспомогательные акценты).
- `signal` — точечный сигнальный акцент (стрелки, маркеры, подчёркивания, узкие
  полосы-кромки). Роль для ЯРКОГО, кричащего тона бренда, который нельзя пускать
  ни в текст, ни в крупные заливки/фон — только в мелкие точечные акценты. В
  neutral: `null` (нейтральный профиль не различает primary/signal). Первый
  профиль, кодифицирующий её — `inache` (00E8E8, «яркая бирюза» в противовес
  спокойному `accent.primary`).
- `on_dark` — акцент, читаемый на ТЁМНОМ фоне (титульный/финальный слайд, section
  divider). Роль для случая, когда `accent.primary` на тёмном фоне нечитаем (тёмный
  акцент на тёмном) — тогда акцентная линия/подзаголовок берут `accent.on_dark`.
  В neutral: `null` (не задаёт; на тёмном фоне используется `text.inverse` — белый,
  см. pptx-strict §3, «Акцент на тёмном фоне»). Бренды со светлоспособным акцентом
  заполняют её (напр. светлый тон акцента). Роль вскрыта обкаткой каталога макетов
  pptx (2026-07-15): у neutral на тёмных слайдах акцент 1F3A5F нечитаем.

### palette.semantic
- `good` / `warn` / `bad` — статусные цвета (KPI, светофор). Общие для всех
  профилей, бренды их не переопределяют.
- `negative_num` — цвет отрицательных чисел (совпадает с `bad` в neutral, но
  роль отдельная, т.к. может отличаться в брендах).
- `zero` — цвет приглушённого нуля в таблицах.
- `delta_positive` — цвет ПОЛОЖИТЕЛЬНЫХ дельт/динамики (прирост, отклонение
  от плана/периода), а не всех положительных чисел вообще (обычные
  положительные значения красятся как обычный текст, не зеленью). В neutral:
  `null` (нейтраль дельты не красит). Светофор `good`/`warn`/`bad` — общий,
  `delta_positive` его не заменяет и не переопределяется им.

### palette.fills
- `header_dark` — тёмная заливка шапки таблицы.
- `section_light` — светлая заливка секционной шапки.
- `callout` — фон выносок/callout-блоков в документах.
- `key_input` — заливка ключевых допущений/драйверов сценария (жёлтый в neutral).
- `paper` — роль «бумага/фон» (общий фон страницы/листа, не заливка отдельного
  элемента). В neutral: FFFFFF.

### palette.chart_categorical
Упорядоченный массив HEX для категориальных рядов диаграмм (секторы doughnut/pie,
серии без встроенной семантики роста/падения/статуса) — НЕ для светофора и НЕ для
дельт. Семантические цвета (`semantic.good/warn/bad`, `delta_positive`) в
категориальных рядах запрещены: категориальный цвет кодирует «какая это
категория», а не «хорошо/плохо». Порядок массива = порядок назначения рядам
(первый цвет — первой категории по данным, и т.д.), переставлять произвольно
нельзя — иначе один и тот же цвет на разных слайдах будет означать разные
категории. В neutral: `["1F3A5F", "6D7F97", "B1BAC7", "808080", "D9D9D9"]` —
построена от `accent.primary` (1F3A5F): осветление на ~35 % и ~65 % (смешение с
белым) дают два производных тона индиго, плюс `text.muted` (808080) и
`lines.row` (D9D9D9) как нейтральные серые для «длинного хвоста» категорий.
Бренд-профили могут переопределять весь массив (например, если у бренда
собственная категориальная гамма) — правило про запрет семантики и порядок
назначения остаётся обязательным.

### palette.excel_conventions
Общеотраслевые Excel-конвенции цвета текста по типу ячейки. **Бренды их не
переопределяют** — это конвенция, а не стиль:
- `input` — синий, хардкод-инпуты.
- `link` — зелёный, ссылки на другие листы книги.
- `extlink` — красный, внешние ссылки (другие файлы).

### typography
Раздельно по среде — у каждой своя роль шрифта и традиция:
- `pptx.primary` + `pptx.roles` (display/semibold/serif/narrow) + `pptx.fallback`.
- `docx.primary` (по умолчанию для внутренних документов) + `docx.external`
  (внешняя рассылка) + `docx.legal` (юридические/госорганы) + `docx.fallback`.
- `xlsx.portable.grid` — шрифт для книг, уходящих за пределы личного контура
  (совместимость важнее). `xlsx.internal.grid` + `xlsx.internal.fallback` —
  шрифт для книг внутреннего пользования (можно фирменный).
- `mono` — моноширинный шрифт (роль `mono.primary` + `mono.fallback`), а также
  `pptx.roles.mono` / `docx.mono` / `xlsx.internal.mono` для среды, где нужен
  моноширинный начерк внутри обычного документа. Область применения моно —
  не решение шрифта, а список ситуаций в `rules.mono_scope` (см. ниже): роль
  существует, но профиль не обязан её использовать вне перечисленных случаев.
  В neutral моно-роль отсутствует (не задана); первый профиль, кодифицирующий
  её — `architekton` (JetBrains Mono).

### rules
Свободная секция точечных стилевых правил профиля (не цвет, не шрифт per se).
Ключи не фиксированы схемой — профиль вводит только те, что ему нужны:
- `emphasis` — способ выделения при отсутствии курсива у гарнитуры
  (`"no-italic"` = вес/цвет вместо наклона).
- `mono_scope` — список ЕДИНСТВЕННЫХ ситуаций, где допустим моноширинный
  шрифт (роль `typography.mono`). Вне перечисленных случаев моно не
  используется — в частности, не в заголовках, корпусе текста, KPI и
  денежных колонках.
- `mono_scope_excludes` — короткая контрформулировка mono_scope для быстрой
  проверки («где моно точно не должно быть»).
- `money_words` — правило записи денежных сумм словами/символом.
- `table_rhythm` — вертикальные/горизонтальные отступы внутри ячеек таблиц.

### number_rules
- `locale` — код локали числового формата, `[$-419]` = русская, пробел-разделитель групп.
- `formats` — именованные маски (money, money_dec, percent, multiple, ratio,
  year_text, year_num, count). Маски скопированы дословно из
  `skills/xlsx-style/references/design-tokens.md` (секция NUMFMT) — там же
  объяснение, почему точный HEX цвета минуса/нуля накладывается условным
  форматированием, а не через сам numfmt.
- `negative.style` — способ обозначения отрицательных (`minus`, не скобки).
- `negative.color_role` / `zero.color_role` — ссылка на роль в `palette.semantic`
  (не дублирование HEX), чтобы бренд, меняющий `semantic.negative_num`,
  автоматически менял и числовой формат.

### brand_marks
Логотипы/водяные знаки/фирменные метки колонтитула. В neutral все `null`
(нейтральный профиль не несёт графических меток). Бренд-профиль заполняет
по мере готовности ассетов. `logo` / `logo_dark` / `watermark` / `footer_mark` —
путь к конкретному файлу ассета (когда он готов). `logo_path` — альтернатива,
когда есть только путь к папке ассетов бренда без готового конкретного файла
(напр. `architekton`: `assets/architekton/logo/` — сами файлы ещё переносятся,
см. `meta.note` профиля).

### xlsx_palette_preset_default
Имя дефолтного пресета из пяти встроенных палитр шапок/секций xlsx-style
(Индиго, Графит, Сине-стальной, Тёмно-зелёный, Бордо). Сами пресеты **не
дублируются в JSON** — они остаются конструкцией скилла `xlsx-style`
(`references/design-tokens.md`, секция PALETTES). Токен-слой хранит только
имя, какой пресет использовать по умолчанию для данного профиля.

## Наследование (inherits)

`"inherits": "<имя>"` означает: сначала загрузить профиль `<имя>` целиком,
затем применить поверх него все секции/ключи текущего файла — рекурсивно
по объектам (глубокое слияние: если в потомке задан только один ключ внутри
`palette.accent`, остальные ключи `palette.accent` берутся от родителя, а
не обнуляются).

Правило переопределения — по ключам, не по секциям целиком: наличие секции
`typography` в дочернем профиле не удаляет остальные секции родителя
(`palette`, `number_rules` и т.д. остаются), и не обязывает переопределять
каждое поле внутри `typography` — только перечисленные.

Пример: `architekton.json` задаёт `"inherits": "neutral"` и переопределяет
`typography` (+ роль `mono`), `rules` (`emphasis`, `mono_scope`, `money_words`,
`table_rhythm`) и точечно палитру: `text.heading/body_screen/muted`,
`lines.row`, `accent.primary`, `semantic.delta_positive`, `fills.paper`.
Ключи палитры, не перечисленные в architekton.json (`accent.secondary`,
`fills.header_dark`, `fills.section_light`, светофор `semantic.good/warn/bad`
и т.д.), наследуются от neutral без изменений — это открытый вопрос до первой
боевой книги (см. `tokens/_architekton-notes.md`, секция «Открытые вопросы»).

`gpbi.json` аналогично наследует `neutral` и переопределяет только
`palette.accent.primary` и часть `palette.fills` — остальная палитра,
вся типографика и number_rules — от neutral.

`neutral.json` — корень наследования, `"inherits": null`.

## Маршрутизация профилей

Скилл выбирает профиль по контексту запроса пользователя:

| Контекст запроса | Профиль |
|---|---|
| «для ГПБИ», упоминание Газпромбанк-Инвест | `gpbi` |
| «Архитектон», личный контур пользователя | `architekton` |
| «Иначе» | `inache` |
| «Пакгауз» | `pakgauz` |
| контекст не указан / не распознан | `neutral` |

Все четыре бренд-профиля (gpbi, architekton, inache, pakgauz) существуют. Если
запрошен профиль, файла которого нет в tokens/ — скилл работает на `neutral` и
явно предупреждает, что бренд-профиль не готов.

## Excel-вопрос-маршрутизатор (portable / internal)

При сборке `.xlsx` скилл `xlsx-style` перед выбором шрифта задаёт (или
выводит из контекста) вопрос: **книга уйдёт за пределы личного контура
пользователя (партнёрам, в банк, во внешнюю рассылку) или остаётся
внутренней?**

- **portable** (уходит вовне, важна совместимость шрифта на чужих машинах) →
  `typography.xlsx.portable.grid` (Calibri — присутствует практически везде).
- **internal** (остаётся в личном контуре пользователя) →
  `typography.xlsx.internal.grid` (+ `internal.fallback`) — можно фирменный
  шрифт бренд-профиля (напр. Golos Text у architekton).

Эта развилка независима от выбора бренд-профиля: profile определяет ЧТО за
шрифт стоит за role `internal.grid`, а portable/internal-вопрос определяет,
КАКУЮ из двух ролей применить в конкретной книге.

## Provenance профиля (происхождение значений и права)

<!-- v2026-07-20: секция заимствована из практики references-manifest (пак Web3nity),
     адаптирована под токен-слой. Обязательна для НОВЫХ профилей; существующие
     дополняются при ближайшей правке. -->

Профиль без записанного происхождения значений через год превращается в набор
«ничьих» hex-кодов и юридический риск (шрифт без известной лицензии нельзя
передавать клиенту). Поэтому каждый профиль сопровождается секцией `provenance`
(в самом JSON или в парном `<профиль>.provenance.md`):

- **для каждого источника**: URL или файл, владелец, дата обращения, что именно
  извлечено (цвета / шрифты / композиционные приёмы);
- **для каждого шрифта**: статус лицензии (`открытая` / `коммерческая, куплена` /
  `коммерческая, статус неизвестен`) и можно ли передавать файл шрифта вовне;
- **для значений**: статус точности по шкале:
  - `confirmed` — из официального брендбука или файла бренда;
  - `observed` — измерено по реальному носителю (сайт, дека) — hex со скриншота
    искажается сжатием и профилем, точность ограничена;
  - `inferred` — обоснованное предположение;
  - `proposed` — авторское решение для этого профиля.

Референс — источник правил, а не материалов: скриншот чужой работы не включается
в выдачу, похожий шрифт не объявляется тем же шрифтом.

## Создание нового бренд-профиля из референсов (фабрика профилей)

Порядок, когда нужен профиль для нового бренда/клиента:

1. **Собрать источники** (приоритет по убыванию): официальный брендбук → файлы
   бренда (лого, шрифты) → сайт и соцсети → референсы-вдохновение. Для каждого —
   запись в provenance.
2. **Разобрать по осям**: палитра и роль акцента, типографика (display/текст),
   композиция и сетка, линии/радиусы, изображения. Каждому значению — статус
   (`confirmed`/`observed`/`inferred`/`proposed`).
3. **Не усреднять конфликтующие референсы**: выбрать главный + поддерживающий
   либо предложить пользователю две явные ветки.
4. **Разложить в роли схемы** (`palette.text/lines/accent`, `typography.*`,
   `number_rules`), заполнив только подтверждаемое; остальное наследуется от
   `neutral` — не выдумывать значения ради полноты JSON.
5. **Проверить тремя носителями**: тестовый слайд (pptx-strict), фрагмент листа
   (xlsx-style), страница документа (doc-style). Роль, которую пришлось
   «угадывать», — сигнал дополнить профиль.
6. **Зарегистрировать** в таблице маршрутизации выше и прогнать
   `validate_tokens.py` на тестовом носителе.

Извлечённый профиль — интерпретация, а не официальная айдентика бренда: пока
статусы не `confirmed`, в коммуникации с клиентом он называется «предложенным
направлением».
